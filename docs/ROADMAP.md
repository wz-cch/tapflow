## 待議的互動設計

**只記錄,還沒改。** 這些是實際用過之後浮出來的,列在這裡是為了不讓它們被當成刻意的設計。

### `💾` 長按 = 另存新片段

**這是權宜作法,不是認可的設計。** 當時存 / 讀檔畫面還沒做完,長按只是暫時的出口。使用者明確表示不喜歡這個做法。

重點在於**不要拿它當「本專案用長按當變體」的前例** —— 它本身就還沒被討論過。真要動的時候連同存 / 讀檔那組畫面一起想。

### 錄製時記下觸點底下的節點文字

**這是唯一會改變「編輯到底能做到什麼」的方向,比任何一顆按鍵都值錢。**

現在列表上是 `47 ▸ 輕觸 540, 1200`。座標不是意義 —— 它沒告訴你那一下按到了什麼。而一份讀不懂的腳本,再多的編輯功能都是在上面盲目動刀,這是 SPEC §9.8 用來砍掉重排、絕對位置搬移、型別互轉的判準。

做法:錄製時順手讀當下觸點底下那個 `AccessibilityNodeInfo` 的文字,存進步驟裡當標籤。列表就變成 `47 ▸ 輕觸「確認」`。讀視窗內容這個能力 M4 為了 `AwaitTextNode` 已經要做(`NodeFinder.kt`),不是新增的架構。

**還沒驗證,先列出已知的坑:**

- 自繪畫面沒有節點可讀 —— Canvas、遊戲、WebView 的一部分,拿到的會是空的或整片一個節點
- `getRootInActiveWindow()` 在錄製的熱路徑上有成本,而錄製最不能容忍的就是延遲(§10 那條逐手勢補發的時序已經很緊)
- 觸點與節點解析之間有時間差 —— 手指離開時畫面可能已經因為那一下而變了,讀到的會是下一頁的節點
- 空標籤要怎麼退回顯示座標,而且不能讓兩種格式在列表裡看起來像兩種東西

### 畫布上的長按

`👁`、拖曳、單擊選取都有主人,**長按目前空著**。雙擊曾經被考慮拿來開設定頁,後來因為設定頁改成從主選單進而不需要了(SPEC §9.7)。

先留白。沒有為了填而填的理由,真的出現需求再指派。

### 已解決,留紀錄

- **等待的秒數改不了** —— 已補。設定頁多了「等待」那一列(SPEC §9.5)。下限一秒,因為 0 秒是等待與手動暫停的分界,允許打 0 等於讓一個數字偷偷換掉步驟型別
- **步驟型別的互轉** —— 決定不做。手動暫停與秒數等待沒有位置資訊,要變成一個點就是刪掉再錄一個;反方向直接按 `⏸+`。互轉這個功能本身沒有比這兩步更短(SPEC §9.4)

## 5. 支援 Shizuku

**排最後,價值待評估。**

Shizuku 提供一個 ADB 權限等級的行程,可以繞過 `AccessibilityService.dispatchGesture` 直接注入輸入事件。

### 會解決什麼、不會解決什麼

| 目前的問題 | Shizuku |
|---|---|
| [#1](https://github.com/wz-cch/tapflow/issues/1) 手勢注入器卡住(固定 ~1010ms) | ✅ **完全解決** —— 直接繞過 `dispatchGesture` |
| app 偵測無障礙服務是否啟用 | ⚠️ 部分 —— 注入可以不靠 a11y,但 overlay 要從 `TYPE_ACCESSIBILITY_OVERLAY` 退回 `SYSTEM_ALERT_WINDOW` |
| [#2](https://github.com/wz-cch/tapflow/issues/2) `filterTouchesWhenObscured` | ❌ **完全沒解** |

**#2 沒解的原因很重要:** `FLAG_WINDOW_IS_OBSCURED` 是關於**畫面上有沒有蓋著視窗**,跟手勢從哪裡注入無關。錄製時還是得掛全螢幕畫布才拿得到座標,還是會遮蔽,那些 app 還是會丟掉觸控 —— 連使用者自己的手指也一樣。

### 成本

- 非 root 的話,**每次重開機都要重新透過 ADB 啟動 Shizuku**。Android 11+ 可用無線偵錯自啟,但仍是門檻
- 使用者要額外安裝 Shizuku app

### 架構影響

小。`GestureDispatcher` 本來就是獨立類別,加一層注入抽象、後面掛兩種實作即可,不需要動 `Player` 或 overlay。
