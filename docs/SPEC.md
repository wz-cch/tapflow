# TapFlow(觸控流)規格書

> v2.0 ‧ 2026-07-25 ‧ 參考同類產品「點擊助手」的互動模式修訂
>
> 開發慣例(Git Flow、commit 格式、分層與語系規則)見 [../CONTRIBUTING.md](../CONTRIBUTING.md)。

Android 按鍵精靈:錄製使用者的觸控操作並自動重播,**不需要 root**,靠 `AccessibilityService` 實現。

**技術棧:純 Kotlin + Jetpack Compose。** 曾考慮 Flutter/Dart,但錄製、重播、懸浮視窗、無障礙服務全都必須原生實作,Flutter 只剩「畫清單」的價值,換來雙倍膠水程式碼與跨 runtime 除錯成本,因此放棄。

**發佈方式:自用側載 APK**,不上 Google Play(Play 對 `AccessibilityService` 的政策要求「必須用於協助身障使用者」,自動化 / 巨集類 app 被下架比例很高)。

---

## 〇、產品形態一句話

> 螢幕上浮著一排工具列。按錄製,你的每個觸控被記下來,同時真的送到下層 app 讓畫面前進;
> 錄完,每一步變成螢幕上一個可拖曳的準心或曲線,你直接拖就改座標;
> 錄到需要輸入驗證碼那種地方,插一個**暫停點** —— 跑到這裡自動停,你手動處理完按繼續;
> 滿意了按儲存變成一個**片段**;多個片段可以串成一條**流程**;
> 按播放,它照著跑。

## 一、技術基礎與關鍵決策

### 1.1 懸浮視窗的實作路徑

工具列與面板**都是**懸浮視窗。「懸浮」有兩種實作路徑:

|  | `SYSTEM_ALERT_WINDOW` | `TYPE_ACCESSIBILITY_OVERLAY` |
|---|---|---|
| 是懸浮視窗 | 是 | 是,行為一模一樣 |
| 需要權限 | 要,且需跳系統設定頁手動開 | **不用** |
| 層級 | 一般 | 更高,可蓋在系統 UI 上 |
| 會被使用者關掉 | 會(「顯示在其他應用上層」開關) | 不會 |
| ROM 相容性 | 成熟穩定 | 小米 / 華為 / OPPO 偶有雷 |

**決策:主用 `TYPE_ACCESSIBILITY_OVERLAY`,掛載失敗時 fallback 到 `SYSTEM_ALERT_WINDOW`。**

- Manifest 宣告 `SYSTEM_ALERT_WINDOW`,但**不主動要求**
- `OverlayHost.attach()` 先試 accessibility overlay;捕捉到 `WindowManager.BadTokenException` / `InvalidDisplayException` 時檢查 `Settings.canDrawOverlays()`,沒有就引導使用者開,再用 `TYPE_APPLICATION_OVERLAY` 重試
- 兩條路徑共用同一份 View 與 `LayoutParams` 建構邏輯,只差 `type` 欄位

一般裝置只要開一個無障礙開關就能用;有雷的 ROM 也不會整個掛掉。兩種都不需要前景服務與常駐通知。

### 1.2 錄製方式:逐手勢補發

無障礙服務**拿不到**其他 app 的原始觸控座標(Android 只給元件層級的 `AccessibilityEvent`,沒有 x/y)。要拿座標只能用全螢幕 overlay 攔截,但攔截到的觸控就不會傳給下層 app。

因此採「盲錄 + 逐手勢補發」:

```
你按下 → overlay 記錄座標 → 你放開
  → overlay 暫時設為 FLAG_NOT_TOUCHABLE
  → 等一個影格,確保 window 重排完成
  → dispatchGesture 把剛剛那個手勢補發給下層 app
  → app 真的反應,畫面前進
  → 清除 FLAG_NOT_TOUCHABLE,等你錄下一步
```

補發期間 overlay 不可觸控,所以**不會有「自己注入的事件被自己攔截」的回音問題**。

用 `FLAG_NOT_TOUCHABLE` 切換而不是 `removeView` / `addView`:文件保證不可觸控的 window 不參與觸控分派,而且沒有 window 重建的閃爍與延遲成本。

代價:每步約 100~200ms 頓挫,快速連續滑動會失準 → 設定裡保留「純盲錄」開關。

### 1.3 面板遮擋問題:靠使用者自己避開

播放中工具列保持可觸控,但**注入的觸控只要落在工具列或播放面板矩形內就會被吃掉,那一步失效** —— Android 觸控分派規則,無法繞過。

**決策:不做自動避讓,靠使用者把工具列拖到空白處。** 自動避讓要處理「移動 window → 等重排 → dispatch → 移回」的時序,複雜度與出錯機會都不低,而把工具列拖到角落就解決了。

**也不做視覺警示。** 曾經在畫布上把工具列與面板矩形畫成斜線警示區(還加過一行文字說明),兩者都已移除:那塊區域使用者本來就碰不到,沒有什麼行為需要被勸阻,而斜線與文字都在錄製時佔掉螢幕。**規格原本要求的「落在警示區內的標記轉黃」也一併取消。**

留下的唯一措施是**在 README 與首次啟動說明寫明這個限制**。而 §3.4 之後,播放時工具列整個不出現、錄製時播放面板不出現,死區本身就縮小了。

自動避讓列為 **M4 可選項**。

**備援中斷手段:音量鍵。** 音量下 = 暫停 / 繼續,長按音量下 1 秒 = 停止。需要 `canRequestFilterKeyEvents="true"` + `flagRequestFilterKeyEvents`。**只在播放中 / 暫停中攔截**,待機與錄製時不攔截,免得平常調不了音量。

### 1.4 只有一種暫停狀態

全 app 只有**一個**暫停機制:`PauseStep`。不管是重播跑到它、錄製時按 `⏸+` 插入它、使用者按暫停鍵、還是 `AwaitTextNode` 等不到目標而超時 —— 進入的都是同一個 `PAUSED` 狀態,只是提示文字不同。

刻意**不做**流程層的獨立暫停節點,也**不做** `Clip.pauseAtEnd`。要在片段之間停下來,就在前一個片段的尾端放一個 `PauseStep`。一個概念一個名字,執行引擎一套暫停 / 恢復邏輯。

**「等待 N 秒」也是同一個型別,不是第二種。** `PauseStep.ms` 為 0 表示等使用者,大於 0 表示等那麼久然後自己繼續。曾經有獨立的 `WaitStep`,已折進來 —— 兩者都是「在這裡停一下」,差別只在誰來解除:計時器還是手指。兩個型別會讓標記、清單文字、執行分支各做兩份,正好違反這一節的原則。

**有秒數的那種不會進 `PAUSED`**,它只是 `RUNNING` 裡的一段延遲,進度照跑。所以 `PAUSED` 仍然只代表一件事:**有事情需要人**。

UI 上仍然是兩顆按鍵(`⏸+` 與 `⏱+`),因為它們問的問題不同 —— 手動那顆不該有對話框(§10.1),有秒數那顆必須先問幾秒。**資料合一,入口分開。**

### 1.5 編輯模式是切換式的

標記可拖曳的同時,下層 app 不可能還正常操作 —— 一個全螢幕 window 要嘛全吃觸控、要嘛全不吃,沒有中間值。

三種可能做法:

| 做法 | 體驗 | 風險 |
|---|---|---|
| **切換式編輯模式** ✅ | 多按一下 | 無,100% 可靠 |
| 每個標記各自一個小 window | 最好 | 錄 100 步 = 100 個 window,效能與 ROM 相容性未知 |
| `addOnComputeInternalInsetsListener` 設 touchable region | 最好 | 非公開 API,Android 9+ 非 SDK 限制可能擋掉 |

**決策:切換式。** 平常畫布 `FLAG_NOT_TOUCHABLE` 完全穿透(看得到標記、拖不動,下層 app 正常用);按工具列的 `✎` 切進編輯模式才整螢幕攔截、才能拖標記。

## 二、架構

單一 process,兩個入口共用 `Repo`(同 process,不需 IPC):

| 元件 | 職責 |
|---|---|
| `MainActivity` (Compose) | 權限引導、片段 / 流程清單、流程編排、全域設定 |
| `TapFlowService : AccessibilityService` | **唯一的執行主體**:掛 overlay、錄製、重播、攔截按鍵 |
| `Repo` (object + StateFlow) | 共享狀態與 JSON 持久化 |

服務負責一切的原因:它是系統綁定的,開關開著就活著不會被殺;只有它能 `dispatchGesture`,也只有它能掛 `TYPE_ACCESSIBILITY_OVERLAY`。

Overlay 全部用**原生 View 而非 Compose**:在 `WindowManager` 上跑 Compose 要自己補 `ViewTreeLifecycleOwner` / `SavedStateRegistryOwner`,服務又沒有 Activity 生命週期,容易踩 recomposer 卡死。主 app UI 才用 Compose。

### 2.1 分層硬規則

| 套件 | 規則 |
|---|---|
| `data\` | **純 Kotlin,不得 `import android.*`,不得含任何使用者可見字串。** 目的是能在純 JVM 上做單元測試,而且所有使用者讀得到的文字都必須落在 `strings.xml`。想在 model 裡放 `label(): String` 就是違規 —— 那是 `text\` 的工作。 |
| `text\` | 使用者可見字串的格式化,吃 `Resources`。Compose 與原生 overlay 共用,所以它不歸在 `ui\` 底下。 |
| `engine\` | 唯一能呼叫 `dispatchGesture` 的地方。 |
| `overlay\` | 原生 View,不用 Compose。 |
| `ui\` | Compose,只有主 app 畫面。 |

### 2.2 語系

介面支援**英文(預設語系)**與**正體中文**,跟隨系統語言,不在 app 內提供切換。

- 所有使用者可見字串都在 `res\values\strings.xml` 與 `res\values-zh-rTW\strings.xml`,**兩邊必須同時更新**,key 順序保持一致以便對照
- 帶參數的字串一律用位置參數(`%1$d`、`%2$s`),不同語言詞序不同
- 這條規則也適用於畫在 overlay 上的字 —— 原生 View 一樣走 `context.getString()`
- 程式碼註解與 commit message 一律英文;規格書與 README 用正體中文

## 三、懸浮視窗

**七個 window。** 三個是常駐主體 —— 工具列(§3.1)、播放面板(§3.2)、標記畫布(§3.3);另外四個是按需掛上、用完就 `remove` 的面板 —— 快捷設定(§3.1)、數字鍵盤(§10.2)、步驟設定頁與步驟列表(兩者都見 §9)。

原則仍是**每個 window 承擔多種形態,而不是一個形態開一個 window**:畫布一個 View 撐三種模式,工具列一個 View 撐展開與摺疊球。那幾個面板之所以沒有併進畫布,是因為它們是十來個控制項的表單 —— 畫在畫布上就得自己做 hit-test,而且會跟標記的 hit-test 打結(§9)。

**設定頁與列表互斥。** 兩者都是置中的大視窗,開一個就關掉另一個。它們最初是小浮動面板,實機測試的第一個問題就是互相重疊擋住視線;讓它們互斥比教它們互相閃避便宜,也讓編輯模式在任何時刻只有一個大介面 —— 設定頁、列表,或乾淨的畫布。

### 3.1 `ToolbarWindow` — 左側垂直工具列

可拖曳、自動吸附左右邊緣,位置持久化。三種形態:

**展開態**(由上到下)

**播放中工具列整個不出現**,所以下表沒有那一欄 —— 見 §3.4。

| 鈕 | 待機 | 錄製中 | 編輯模式 | flow |

| ⧈ | **模式:片段**(按了切流程) | — | — | **模式:流程**(按了切片段) |
| ▶ | 播放 | — | — | **播這條流程**(不同 icon;沒載入流程時變灰) |

**主選單是一個容器,裡面只放這個畫面用得到的功能。** 用不到的鍵不是變灰,是**不出現**;總長度不是問題,因為按鍵區可以捲動。所以編輯模式不是「待機那一組再加幾顆」,而是自己的一組。

幾個決定的理由:

- **編輯模式沒有 `💾` `📂` `⊕` `▶` `▶|` `⚙`** —— 存檔、讀檔、開新片段、播放、設定,都是「擁有一份腳本」在做的事,不是「修改一份腳本」在做的事
- **`↩` 只在錄製與編輯** —— 它存在的條件是這個模式能改動步驟。待機能播能存,但不能改,所以沒有東西可以復原
- **插入一律往後,沒有例外。** 方向改由設定頁的 `«` `»` 移動鍵承擔,理由見 §9.3
- **`⏸+` 不放待機** —— §10.1 定義非錄製狀態按它是「插在選取後面」,但待機時不可能有選取(選取只在編輯模式存在),所以它永遠只能附加在尾端
- **flow mode 為什麼這麼薄** —— 見 §10.4
- **`⧈` 在錄製與編輯不出現** —— 那兩個是 clip mode *裡面*的狀態,離開它們是 `⊙` 和 `✎` 的事
- **`⧈` 固定在最上面** —— 它是唯一會改變其他按鍵含義的鍵,不能隨按鍵組浮動(§10.5)
- **`⚙` 不放錄製** —— 唯一會想在錄製中當場改的是逐手勢補發,而它正常就是開著的
- **`✕` 不放錄製** —— 它會關掉整個懸浮工具列,而那是停止錄製的唯一入口

**按鍵區可捲動。** 上表宣告 25 顆鍵,最多一次顯示 13 顆,橫向螢幕仍可能放不下,所以按鍵區包在一個高度上限夾在螢幕內的 ScrollView 裡。**拖曳把手刻意留在捲動區外面** —— 放在裡面 ScrollView 會攔走垂直拖曳,工具列就再也拖不動,等於把一個摸不到的控制換成另一個。

**快捷設定面板(`⚙`)** —— 放「人在現場才會想改」的設定:迴圈次數、速度、逐手勢補發、螢幕常亮、黑幕、計時器、工具列大小與不透明度。

> 這是實機回饋加的。原本所有設定只在主 app 裡,結果要改個迴圈次數或開黑幕,就得切出目標 app、改一個數字、再切回來。判斷標準是**設定的效果是否需要當場看到**:需要的放面板;只在「新增動作時」才被讀取的(預設點擊 / 滑動時長)留在 app,那裡才有空間解釋。面板底部有連結直接跳到完整設定。
>
> 面板上的開關用自繪的 pill 而不是 `Switch`:`Switch` 會吃 app 的主題(淺色),放在這些深色面板上會像壞掉的。數值加減先對齊到刻度再 clamp —— 浮點反覆相加會飄,`0.7000001` 會卡在範圍邊界動不了。

**沒有獨立的「暫停錄製」鍵** —— 因為 `⊙` 是附加語意,`⊙ → ■ → 做別的事 → ⊙` 本身就是暫停與接續。少一顆鍵。

`↩ 復原` 從 M1 就要有:錄製恢復是立即生效不倒數的(§10.1),誤錄在所難免。

**它不是「刪掉最後一步」,跟 `−` 不重疊。** M1 的實作確實是 `dropLast(1)`,字面上就是移除尾端 —— 而那個名字(「復原上一步」)留到了實作換掉之後,讀起來像是「刪除第 100 步」,跟 `−`「刪除選取」擺在一起就變成兩顆看起來都在刪東西的鍵。現在 `Workspace` 存的是狀態快照堆疊,`↩` 復原的是**上一次改動**,不管那是拖曳、插入、改時長還是刪除。

差別在實際使用上是這樣的:選到第 47 步,不小心把它拖走 200px —— `−` 救不了(它只會把 47 刪掉),`↩` 會把它放回原位。所以字改成「復原」,行為不動。

**它現在是真的復原,不是「刪掉最後一步」。** 原本的實作是 `steps.dropLast(1)`,所以只救得回最近一次錄製 —— 拖錯、刪錯、插錯都救不回來,編輯模式等於沒有任何退路。改成快照堆疊:`steps` 是不可變 `List`,所以一筆快照就是一個參考而不是複製,代價幾乎為零。

一次拖曳只留一筆快照(每個觸控取樣都存會讓堆疊塞滿中間位置而失去意義)。載入片段與「開新的」會清空歷史 —— 跨過那兩個邊界復原會把別的片段的步驟變出來。

**摺疊態** — 56dp 圓球,顏色示意狀態(灰 待機 / 紅 錄製),球面顯示當下唯一有意義的動作。可拖曳,點一下展開。

球只有兩種意思:**展開**,或**繼續錄製**。沒有「繼續播放」——播放時工具列根本不出現(§3.4),繼續與停止都在播放面板上。

除了手動按 `∧`,**按 `⏸+` 插入暫停點時**會自動摺疊成球並移到螢幕上半部,把鍵盤區讓出來 —— 見 §10.2(2),這是人工介入能不能真的用的關鍵。播放暫停不需要這個動作:整個工具列都不在,鍵盤區本來就是空的。

**`✕` 是關閉,不是縮小。** 按下去會把懸浮開關關掉,並 toast 告知回主 app 重新開啟。

> **這裡原本的設計是錯的,實機驗證後改掉。** 原規格是「`✕` 收起成一條 6dp 寬的邊緣細條,點一下彈回」。實機上 6dp 根本不是可觸控的尺寸,而且因為 `toolbarForm` 沒有被重設,按下 `✕` 之後**沒有任何辦法把工具列叫回來** —— 主 app 的開關關掉再開、甚至把無障礙服務關掉再開,回來的都還是同一條點不到的細條。
>
> 現在:摺疊只有圓球一種形態(56dp,高於 48dp 最小觸控目標);`✕` 語意改成誠實的關閉,主 app 的開關會同步反映;而且**每次掛載 overlay 都強制重設回展開態**並重新 clamp 位置,所以開關永遠會給出一個看得到、按得到的工具列。

**位置容錯** — overlay 掛上時,以及 view 量測完成後,都會把座標 clamp 回螢幕範圍內。存在偏好裡的位置可能來自不同尺寸的螢幕或不同方向,不夾一次會停在畫面外。

大小與不透明度由全域設定調整(§7)。

### 3.2 `TransportWindow` — 頂部橫向播放面板

窄扁形狀,預設貼頂部中央,可拖曳。刻意做窄,降低擋到手勢座標的機率。

```
┌──────────────────────────────────────────┐
│  ■   ⏸   │  🔁 02      ⤳ 07 / 23         │
│          │       00 : 01 : 34            │
└──────────────────────────────────────────┘
   停止 暫停   迴圈次數    步驟進度   計時器
```

**只在倒數 / 播放 / 暫停時顯示** —— 也就是工具列不出現的那三種狀態。錄製與待機時隱藏:錄製時停止鍵在工具列上,面板只會多蓋一塊錄不到的區域。計時器可在設定關閉。

### 3.3 `CanvasWindow` — 標記畫布(一個 View 三種模式)

全螢幕。同一個 `CanvasView` 依模式改變行為:

| 模式 | 觸控 | 畫什麼 |
|---|---|---|
| **唯讀**(待機 / 播放) | `FLAG_NOT_TOUCHABLE` 完全穿透 | 所有步驟的標記;播放中高亮當前步驟;可選亞光黑幕 |
| **編輯**(按 `✎`) | 整螢幕攔截 | 標記 + 選取框(設定頁與列表是另外兩個 window) |
| **錄製**(按 `⊙`) | 整螢幕攔截 + 逐手勢補發 | 半透明底色 + 即時新增的標記 |

亞光黑幕畫在這個 View 上,不需要額外 window。**設定頁與步驟列表不是** —— 各自是自己的 window,理由見 §9.5、§9.6。

### 3.4 工具列與播放面板永不同時出現

> **錄製情境用工具列(展開 → 球),播放情境用播放面板。**

| 狀態 | 工具列 | 播放面板 |
|---|---|---|
| 待機 | 展開 | — |
| 錄製中 | 展開 | — |
| 錄製暫停(`⏸+` 後) | 球(⊙ 繼續錄製) | — |
| 播放倒數 | — | 倒數 + ■ |
| 播放中 | — | ⏸ ■ 進度 計時 |
| 播放暫停 | — | ▶ ■ + 暫停提示 |
| 編輯 | 展開 | — |

**為什麼不是「所有暫停狀態都用面板」。** 一度考慮過,但那會弄壞錄製暫停:`⏸+` 會停止錄製並回到 `IDLE`,而面板在 `IDLE` 不顯示。球也拿掉的話,打完驗證碼就沒有任何東西可以按來接續 —— 而那個流程是 §13 說的產品差異點。照上表分,錄製側完全不用動。

**為什麼重要,不只是視覺。** 停止鍵原本在工具列與面板上各有一份。而每多一個懸浮視窗就多一塊死區(§10.3):錄製時錄不到、播放時那一步會被吃掉。播放與錄製各少一個 window,死區就各少一塊。

**實作上不要新增「隱藏」形態。** 由 mode 推導出來,不要存成第三種 `ToolbarForm` —— §3.1 記著 `✕` 那次「工具列再也叫不回來」,起因正是把形態存起來而沒有重設。推導出來的隱藏不可能卡住:mode 一變,工具列自己回來。

## 四、工作區與儲存模型

**工作區(Workspace)= 記憶體中「目前螢幕上這組動作」。** 這是使用者直接操作的對象。

```
⊙ 錄製      新錄的動作【附加】到工作區尾端(不清空)
＋          錄一個手勢,插在選取【之後】(沒選就是尾端)
⧉           複製選取,插在它之後
−           刪除選取的標記
拖曳標記     改座標
⚏ 設定頁     類型 / 座標 / 等待秒數 / 備註 / 時長 / 前置延遲 / 重複次數與間隔 / 前後移一格 / 複製 / 刪除 / 翻頁 / 跳到第 N 步
☰ 列表       整頁列出所有步驟,點一列就選它並開設定頁
▶ 播放      直接跑工作區內容,不需要先儲存
💾 儲存      存成片段(Clip)—— 可覆蓋來源片段,或另存新片段並命名
```

**錄完不自動存。** 留在工作區讓你拖曳微調,滿意了才按 `💾`。這正是「可拖曳編輯」存在的理由:錄完馬上就能修。

### 4.1 存 / 讀 / 開新的

三顆按鍵,各自跳一個只做一件事的小畫面:

| 鍵 | 畫面 |
|---|---|
| `💾 儲存` | 名稱輸入框。載入自某片段時預設**覆蓋**它,勾選才另存新的 |
| `📂 讀取` | 片段清單,點一下載入。工作區有未儲存變更時先警告讀取會取代 |
| `⊕ 開新的` | 「會清空畫面上的 N 個動作」→ 清空 |

**做成 Activity 而不是 overlay 面板。** 命名需要輸入框,輸入框需要輸入焦點,而這裡的懸浮視窗一律 `FLAG_NOT_FOCUSABLE` —— 那正是暫停點能用的前提(不搶下層 app 的輸入法)。一個 Activity 三種模式,共用同一個透明主題與 manifest 條目。

`⊕ 開新的` 這顆的存在理由:`⊙` 是附加語意,所以在有它之前,錄完一段**沒有任何方式**開始下一段。

### 4.2 自動草稿

工作區每次變動就寫入 `filesDir/workspace.json`,**但只有 dirty(有未儲存變更)才會在服務重啟後還原。**

> 原本是無條件還原,結果存過的片段也會自己回來,看起來像 app 擅自開檔。草稿的用意是保護**還沒存過**的錄製 —— 存過的已經是片段了,要它回來就按 `📂 讀取`。

## 五、資料模型(三層)

### 5.1 最小動作層

多指手勢要支援,所以**統一成 stroke 模型**,不分 Tap / Swipe 類別:

```kotlin
@Serializable data class Pt(val x: Float, val y: Float, val t: Long)  // t = 相對該 stroke 起點的 ms

@Serializable data class Stroke(
    val points: List<Pt>,
    val startOffset: Long = 0,   // 相對整個手勢起點的 ms(多指時各指下手時間不同)
)

@Serializable sealed interface Step {
    val id: String          // 穩定識別,拖曳 / 選取 / 排序都靠它
    val delayBefore: Long   // 執行前要等多久
}

@SerialName("gesture") data class GestureStep(val id: String, val strokes: List<Stroke>, override val delayBefore: Long) : Step
@SerialName("global")  data class GlobalStep(val id: String, val kind: GlobalKind, override val delayBefore: Long) : Step
@SerialName("pause")   data class PauseStep(val id: String, val note: String = "", val ms: Long = 0, override val delayBefore: Long = 0) : Step

enum class GlobalKind { BACK, HOME, RECENTS, NOTIFICATIONS }
```

**統一 stroke 的理由**:點擊是 1 條 1 點的 stroke,滑動是 1 條多點的 stroke,雙指縮放是 2 條 stroke。重播引擎因此只有一條程式路徑(逐 stroke `GestureDescription.addStroke`),不用寫三份。UI 顯示與繪製時用 `describe()` / `markerOf()` 反推語意:

| 條件 | 顯示文字 | 螢幕標記 |
|---|---|---|
| 1 stroke、位移小、< 500ms | 點擊 (x, y) | 藍色十字準心 + 序號 |
| 1 stroke、位移小、≥ 500ms | 長按 (x, y) ‧ 800ms | 準心 + 外圈進度環 |
| 1 stroke、位移大 | 滑動 (x₁,y₁) → (x₂,y₂) ‧ 240ms | 橙圈起點 + 灰色粗曲線 + 箭頭終點 |
| 2+ strokes | 2 指手勢 ‧ 480ms | 同序號多條軌跡,色相不同 |

`delayBefore` 由錄製時前後兩次觸控的時間差算出,重播才有原本的節奏。

### 5.2 片段層(Clip)= 儲存下來的一組動作

```kotlin
@Serializable data class Clip(
    val id: String,
    val name: String,
    val steps: List<Step>,
    val screen: ScreenSpec,             // 錄製當下的螢幕條件
    val createdAt: Long,
    val updatedAt: Long,
)

@Serializable data class ScreenSpec(val width: Int, val height: Int, val rotation: Int)
```

### 5.3 流程層(Flow)= 把片段串起來

```kotlin
@Serializable data class Flow(
    val id: String,
    val name: String,
    val clips: List<ClipNode>,
    val loopCount: Int = 1,        // 0 = 無限循環
    val createdAt: Long,
    val updatedAt: Long = createdAt,
)

@Serializable @SerialName("clip")
data class ClipNode(
    val clipId: String,
    val delayBefore: Long = 0,     // 這個片段開始前等多久
    val repeat: Int = 1,           // 這個片段原地跑幾次
    val repeatIntervalMs: Long = 0,// 那幾次之間隔多久
)
```

**這一層只有一個型別,而它跟步驟層是同一個形狀,往上長一層:**

| 容器 | 成員 | 每個成員的旋鈕 | 容器自己的旋鈕 |
|---|---|---|---|
| **片段** | 步驟 | `delayBefore`、重複次數、重複間隔 | 迴圈次數(全域 / 每次執行) |
| **流程** | 片段 | `delayBefore`、重複次數、重複間隔 | `loopCount` |

原本這一層有四個型別。`WaitNode` / `GlobalNode` / `AwaitTextNode` **是下一層概念的複製品** —— `WaitNode(ms)` 跟 `PauseStep(ms)` 是同一個欄位,連顯示字串都共用 `step_wait`;`GlobalNode(kind)` 是功能較少的 `GlobalStep`。**node 就是步驟**,所以流程的成員只有片段:

- 要在片段之間等 → `ClipNode.delayBefore`
- 要在片段之間按返回 → 在前一個片段尾端放一個 `GlobalStep`
- **條件等待(M4)回到步驟層,不是節點** —— 「等到出現『登入成功』」在片段**中間**比只能放在片段**之間**有用得多

這也讓原本預留的 `pauseAfter` 旗標**不必做**:它要解的「同一片段重用在不同流程、有的要暫停有的不要」,`delayBefore` 已經解掉,而且是長度而不是布林。

**`Flow` 沒有 `startDelayMs` 與 `speed`** —— 那兩個在 `Settings` 已經有了,同一個數字放兩個地方遲早不一致。

**`Flow` 也沒有「未儲存」狀態** —— 它是引用清單,編排畫面一改就直接寫回。所以 flow mode 沒有存檔鍵,而丟棄的警告也只有單邊(§10.4、§10.6)。

**兩層迴圈**:`Flow.loopCount` 是整體重播次數,`ClipNode.repeat` 是該片段自己重複幾次。例:登入片段跑 1 次,點擊片段跑 500 次。

**執行不新增執行器** —— 流程展開成一條步驟清單交給既有的 `Player`,見 §13 M3。

**序列化注意**:`Json { classDiscriminator = "type" }`。**不能用 `"kind"`**,會跟 `GlobalStep.kind` 撞名,kotlinx.serialization 會在執行期丟例外。

儲存分兩處,見 §12.1:**存好的片段與流程在使用者指定的資料夾裡**(`clips/<名稱>.json`、`flows/<名稱>.json`),工作區草稿與設定留在 `filesDir`,overlay 位置與偏好放 SharedPreferences。

## 六、執行引擎

### 6.1 狀態機

```
IDLE
 │ play(工作區 或 片段 或 流程)
 ▼
COUNTDOWN(3→1) ──stop──▶ IDLE
 │
 ▼
RUNNING ──使用者按暫停 / 跑到 PauseStep / AwaitText 超時──▶ PAUSED
 │  ▲                                                                    │
 │  └──────────────── resume ──────────────────────────────────────────┘
 │                                                                       │
 └──stop──▶ IDLE ◀──stop(游標清除,下次從頭)──────────────────────────┘
 │
 ▼ 跑完
DONE ──▶ IDLE
```

「結束」= 回到待機、游標清空;下次按播放**從頭跑**,不是立刻自動重跑。

游標:

```kotlin
data class Cursor(val loop: Int, val nodeIndex: Int, val nodeRepeat: Int, val stepIndex: Int)
```

**實作要點:暫停不要 cancel job。** 用單一 coroutine Job 跑整個流程,暫停時在檢查點上 `pauseFlag.first { !it }` 掛起 —— 游標自然保留在區域變數裡,不需要序列化或還原。`stop` 才 `job.cancel()`。這比「cancel 後從序列化游標恢復」簡單一個數量級。檢查點放在每個 step 執行前、每個 node 進入前。

同時只能跑一個流程。

### 6.2 座標處理管線

每個 stroke 的座標依序經過:

```
原始座標
  → 解析度縮放(curW/recW, curH/recH)
  → 隨機位置抖動(整條軌跡套用同一個位移向量)
  → clamp 到螢幕範圍
  → GestureDescription.StrokeDescription
```

**抖動是整條軌跡一起偏移,不是每個點各自抖** —— 每點各自抖會讓滑動軌跡變成鋸齒。

時間軸同樣套用:`delayBefore` 與 stroke duration 各自 ±`jitterTimePercent`%,再乘上 `speed` 倍率。

### 6.3 螢幕方向與解析度

`Clip.screen` 記錄錄製當下的 width / height / rotation。播放前:

- **rotation 不同** → 進入 `PAUSED`,提示「此片段錄製於橫向,請轉回橫向後按繼續」
- **尺寸不同** → 線性縮放,UI 上標示「已縮放」

不做圖像比對,跨機型可靠度有限。

### 6.4 螢幕常亮與亞光

長時間掛機時螢幕一熄,`dispatchGesture` 全部無效。

- **常亮**:錄製 / 播放期間,`CanvasWindow` 的 `LayoutParams` 加 `FLAG_KEEP_SCREEN_ON`,結束移除。零權限、零額外宣告。
- **亞光**:設定開啟後,`CanvasView` 在唯讀模式下畫一層黑色 `alpha = dimAlpha` 的全螢幕矩形。因為播放時畫布是 `FLAG_NOT_TOUCHABLE`,**不會吃掉注入的手勢**。工具列與播放面板在其上方仍可見可按。

亞光會讓你看不到目標 app,只適合純掛機 —— UI 上要說明。

### 6.5 一步沒送到的時候:兩個政策,不是一個

一步失敗有**兩種**,它們從同一個 callback 回來,但需要相反的處理。原本各有一條寫死的規則,而且是反的:取消永遠暫停且關不掉,拒收與注入器不見永遠繼續 —— 也就是**最可能救得回來的那種會停,而「根本沒送到」的那兩種會走下去**。

| 觸發 | 下層 app 收到什麼 | 能不能重試 | 政策 |
|---|---|---|---|
| **取消**(`onCancelled`) | 我們送出的那一部分 **+ 你的手指**,兩個都收到 | **不能** | `TouchPolicy`:中斷 / 暫停 / 忽略 |
| **拒收 / 注入器不見** | **什麼都沒收到** | 可以 | 重試 N 次,然後 `FailurePolicy`:略過 / 暫停 |

**為什麼取消不能重試:** 真實輸入一到,framework 立刻取消進行中的注入手勢 —— 兩個輸入流不會合併,真實輸入直接贏。所以那一步已經**部分送達**,重發等於把半個滑動疊在自己上面。而且這件事的性質是「有人伸手接手」,不是故障。

`onCancelled` **不帶任何理由**,所以「是手指」是推論:其餘會造成取消的原因都是這個 app 自己控制並避開的(從不同時派送兩個手勢、播放期間刻意不動畫布),而注入器不見那一種在 `GestureDispatcher` 裡就用**時間**分掉了 —— 它固定落在一秒附近,與手勢長度無關。

**兩個都預設暫停。** 第 3 步沒落地、然後 4 到 40 步照跑完並回報成功,是那種「看起來成功的失敗」,那才值得打斷。

**重試上限 10,而且讀進來就夾。** 注入器不見不會自己好(要 toggle 服務或重開機),所以對它的每一次重試都會失敗,每次還要付 framework 那一秒的逾時。

**略過會回報。** 選略過的意思是「少一下點擊沒關係」,而那個前提只在你相信那些點擊發生過時才成立。所以次數在**結束時講一次** —— 不打斷是選它的目的,不被告知是另一回事。

`GestureDispatcher` 自己那兩個重試留在原地(重新註冊服務後試一次、取消得太早所以什麼都沒送出時試一次)。那兩個是**辨認出特定故障然後修它**,這裡的迴圈是**表達偏好**,層級不同。

## 七、全域設定

```kotlin
@Serializable data class Settings(
    // 新增動作時套用的預設值
    val defaultGapMs: Long = 50,        // 動作間隔
    val defaultTapMs: Long = 75,        // 輕觸並按住
    val defaultSwipeMs: Long = 300,     // 滑動持續
    val defaultPinchMs: Long = 3000,    // 兩指縮放持續

    // 執行
    val defaultLoopCount: Int = 1,      // 0 = 直到按停止
    val speed: Float = 1f,
    val startDelayMs: Long = 3000,

    // 一步沒送到的時候(見 6.5)
    val onRealTouch: TouchPolicy = PAUSE,       // 中斷 / 暫停 / 忽略
    val failureRetries: Int = 1,                // 0 = 立刻放棄,上限 10
    val onGestureFailure: FailurePolicy = PAUSE, // 略過 / 暫停

    // 隨機抖動
    val jitterRadiusPx: Int = 0,        // 0 = 關閉,上限 150
    val jitterTimePercent: Int = 0,     // 延遲與時長 ±N%

    // 錄製
    val replayEachGesture: Boolean = true,  // 逐手勢補發;關掉就是純盲錄
    val replayDelayMs: Long = 80,           // 補發後等目標 app 動畫的時間

    // 外觀
    val uiScale: Float = 1f,            // 0.7 ~ 1.5
    val uiOpacity: Float = 1f,          // 0.3 ~ 1.0
    val showTimer: Boolean = true,
    val markerDensity: MarkerDensity = MarkerDensity.RECENT,

    // 螢幕
    val keepScreenOn: Boolean = true,
    val dimOverlay: Boolean = false,
    val dimAlpha: Float = 0.85f,
)

enum class MarkerDensity { ALL, RECENT, HIDDEN }
enum class TouchPolicy { STOP, PAUSE, IGNORE }
enum class FailurePolicy { SKIP, PAUSE }
```

主 app 提供「恢復成預設值」。

### 7.1 數字可以打字,而且是逐列選擇加入的

滑桿對「看得見全部」的範圍夠用,對看不見的完全不行。迴圈次數就是逼出這件事的那一個:**「永遠循環」是 0,0 是 0–500 滑桿最左邊那一個像素,而「永遠循環」四個字要滑到才會顯示** —— 設定一直在,只是找不到。所以無限循環不需要新功能,只需要能把數字說出來。

**逐列加入,不是全部自動,而這正是它的設計重點。** 有四列**顯示的數字不是儲存的數字**:速度與工具列大小顯示倍率,不透明度與黑幕濃度把 0–1 的分數顯示成百分比。一個直接接到滑桿單位的輸入框會把不透明度的「85」寫成 85(而不是 0.85),**靜默地**,而且不在任何會被擋下來的範圍之外。

所以 `TypedNumber` 用**顯示的單位**給值,自己帶轉換回去;而兩種單位不一致的那幾列**乾脆不提供**輸入 —— 它們的範圍很窄,窄範圍正是滑桿擅長的。

兩個小規則:

- **打進去的值照原樣採用,不套滑桿的 granularity。** granularity 存在的目的是讓**拖**落在整數上;打字就是繞過它的手段,把 137 ms 圓成 150 會把唯一一個刻意精確的輸入丟掉
- **超出範圍是拒絕,不是夾。** 夾會把打錯的 5000 變成看起來被接受的 500,而且那一列本來就沒有任何地方寫著上下限 —— 顯示範圍並拒絕,同時把上下限講出來

## 九、編輯模式的互動

按 `✎` 進入後,整螢幕由畫布攔截。

**編輯模式只有兩個面:畫布負責位置,設定頁負責其他全部。**

畫布不適合選取 —— 100 步的標記互相重疊 —— 但它是唯一能拖的地方。所以把選取搬進設定頁,畫布只留它唯一擅長的事。

| 操作 | 行為 |
|---|---|
| 拖曳序號徽章 | 整個手勢平移 |
| 拖曳滑動的箭頭尖端 | 改變方向與長度,**繞起點做旋轉縮放**,所以曲線形狀會保留 |
| 點一下標記 | 選取(僅此;不會彈任何面板) |
| 點空白處 | **不做任何事**(見下方「選取永遠存在」) |
| 工具列 `⚏` | 開設定頁,開在當下的選取上 |
| 工具列 `☰` | 開步驟列表 |
| 工具列 `＋` | 錄一個手勢,插在選取之後 |
| 工具列 `⧉` | 複製選取,插在它之後 |
| 工具列 `−` | 刪除選取,後續序號自動遞補 |

實際跑起來的循環:`⚏` → 翻到第 47 步 → 關閉 → 畫布上只有 47 這個標記 → 拖 → 再按 `⚏`。

### 9.1 選取永遠存在

**編輯模式下「沒有選取」這個狀態不存在。** 選取預設落在最後一步,刪除後移到接手的那一步,所以只要工作區非空,選取就是一個有效的索引。

這不是為了方便,是為了消掉一整批特例:隔離沒有東西可以隔離、插入與刪除沒有錨點、設定頁沒有東西可以開 —— 全部來自同一個空狀態。而最後一步在工作區存在時必定存在,所以這個狀態可以直接不要。

點空白處因此不清除選取:清掉之後會立刻被補回最後一步,讀起來像 app 自己跳走。

### 9.2 隔離 = 只顯示選取的那一個

`👁` 在編輯模式是隔離開關(在其他模式仍是三段密度)。開著就是**一個標記,沒有例外**。

- 100 步、隔離關 → 100 個標記
- 100 步、隔離開 → 第 100 個(因為選取預設在最後一步)
- 刪掉它 → 變第 99 個

**刪除一律往前一格**,所以上面那條在腳本中間也成立:刪掉第 47 步,選取落在第 46 步,你留在剛做出來的缺口**後面**而不是站在缺口上。第一步例外 —— 它前面沒有東西,所以補上來的那一步就是你剩下的。刪光了就離開編輯模式,因為沒有東西可以編輯。

規則一致,而且**不需要退回值** —— 早期版本在「沒有選取」時退回顯示全部,結果「隔離」偶爾等於「顯示全部一百個」,正好是它要關掉的那件事。§9.1 之後那個情況不存在了。

隱藏的標記也不參與 hit-test:看不到的東西不該抓得到。需要用眼睛找標記時關掉隔離。

### 9.3 插入一律往後;方向長在移動鍵上

**四顆插入鍵(`＋` `⧉` `⏸+` `⏱+`)一律插在選取之後,沒有例外。** 這是錄製生長的方向 —— 你加進腳本的每一步都落在前一步後面。選了 47,新的就是 48;沒選就落在尾端,同一條規則。

要放到第 1 步前面就是**插完往前移一格**。

`insertBefore` 是更能表達的原語,一度掛在設定頁上寫明「往前插」。拿掉的理由不是它不好用,是**四顆插入鍵裡只有一顆帶方向,那一顆就會讀成例外而不是規則** —— 而且它跟主選單的 `＋` 方向相反,是會踩到的。

所以方向搬到 `«` `»`,那裡它本來就無法迴避:一顆移動鍵不可能沒有方向。插入因此變成一條沒有例外的規則。

**只做 ±1,不做絕對位置。** 「移到第 N 步」討論過並砍掉:它服務的是重構腳本,而重構的前提是讀得懂腳本 —— 一百步用座標標示是讀不懂的(見 §9.11)。真實的需求是插完那一下的微調,那時候你完全知道自己剛做了什麼。

**「錄反了要換順序」也不是留下它的理由。** 要發現第 5 第 6 反了,得先知道那兩步各自在做什麼,而那正好是做不到的事。

### 9.4 「新增一步」與「重錄一步」跟「錄製」是同一件事

三者都是「把手指放到螢幕上,讓它變成一步」,差別只在結果落在哪裡。所以只有一條擷取路徑(`CanvasView` 全螢幕攔截並回報 strokes),後面三種處置:

| 呼叫者 | 落點 | 前置延遲 | 逐手勢補發 |
|---|---|---|---|
| 錄製 | 附加到尾端 | 用時鐘量測 | 開 |
| `＋` | 插在選取之後 | 全域預設值 | 關 |
| 「重錄」 | 取代該步的 strokes,id 不變 | **保留原本的** | 關 |

- **前置延遲不量測**,因為時鐘在你找工具列按鍵的時候還在跑,把那段時間記進去等於插進一個「你猶豫了多久」的暫停
- **重錄保留前置延遲**,因為延遲是這一步跟鄰居之間的節奏,重做動作不是丟掉節奏的理由(它在設定頁上可以單獨改)
- **編輯時不補發**,因為補發存在的理由是讓錄製中的 app 跟著你往前走,而編輯時沒有這樣一趟路要同步

這也解掉了原規格「手動新增只做點擊點」的限制:`＋` 擷取真手勢,所以手動加的一步可以是錄製能產生的任何東西。

**刻意沒有「在螢幕中心生一個點再拖過去」。** 那是兩個動作換一個點,而且兩個都不是你已經會的那個動作。

**刻意沒有「重新指定座標」。** 編輯模式可以直接把標記拖過去,而重錄涵蓋了拖曳做不到的部分(滑動的路徑、時長)。

**刻意沒有型別轉換。** 手動暫停與秒數等待沒有位置資訊,要把它變成一個點就是刪掉再錄一個;反方向也一樣,直接按 `⏸+` 即可。

### 9.5 設定頁

置中的大視窗,**刻意跟標記的位置無關** —— 它顯示的是數字和按鍵,貼在標記旁邊只會讓它變小、擋住標記、還跟列表撞在一起。

```
┌──────────────────────────────────────┐
│  ‹    47 / 100    ›     [跳到]    ✕  │
├──────────────────────────────────────┤
│ 點擊                                  │
│ 540, 1180                    [重錄]  │
│ 等待        3 秒             [變更]  │
│ 沒有備註                     [備註]  │
│ 時長        75 ms          −     +   │
│ 前置延遲    320 ms         −     +   │
│ 重複        ×10             [變更]  │
│ 重複間隔    200 ms         [變更]  │
│ [«] [複製]              [刪除] [»]  │
└──────────────────────────────────────┘
```

- **只會開在某一步上,不存在「不帶步驟開啟」。** 所以不會有「預設第一步再靠翻頁走過去」的情況,而**上一頁 / 下一頁**在這裡就單純是「同一個面板,換一步」
- **出口只有一個:關閉就回畫布。** 面板因此不需要記住是誰開的。要回列表就再按一次 `☰`
- **「跳到第 N 步」在這裡,不在列表裡。** 播放回報的是編號(`⤳ 47 / 100`),知道編號時輸入最快;列表是給不知道編號、要靠讀出來認的情況
- **「等待」那一列是秒數可改的地方。** 在它存在之前,等待的長度只能在插入的那一刻設定一次 —— 因為面板對沒有座標的步驟不顯示任何一列,而那正好就是等待。下限一秒:0 秒是等待與手動暫停的分界,在這裡打 0 會偷偷換掉步驟型別
- **備註那一列只是顯示 + 一顆按鍵**,按下去跳 `WorkspaceDialogActivity` 才輸入 —— 它跟其他 overlay 一樣 non-focusable,拿焦點會搶掉下層 app 的輸入法
- **複製、刪除、前後移四顆都在**,而且都讓面板留在「這個動作留下的那一步」上:複本、刪除後的前一步、或同一步的新編號。刪除一開始被擋下來,正是因為「按完面板要去哪」沒有答案;答案定下來(往前一格)之後那個顧慮就沒了
- **複製與刪除跟主選單共用同一段程式**(`duplicateSelected()` / `deleteSelected()`)。兩個入口一種行為沒問題,兩份實作才會慢慢不一致
- **移動鍵擺在兩端,各自在它指的那一邊。** 中間留給另外兩顆,而中間那段彈性空白把複製與刪除拉到這一排能做到的最遠 —— 伸手要按一顆卻按到另一顆,只有其中一顆的代價是貴的
- **移動鍵用雙箭頭 icon,不用文字。** 標頭的單箭頭移動的是**你**,這裡的雙箭頭移動的是**這一步**,要一眼分得出來;而且翻譯後的「往前移」長度各語系差很多,足以把這一排推歪
- **到頭了就變灰,不隱藏。** 一顆到端點就消失的按鍵會讓整排橫移,而這排的重點正是兩端各自握著它指的方向
- **「從第 N 步開始播」也不在這裡,在待機工具列上**(`▶|`)。決定一次執行從哪裡開始是**執行**的性質,不是編輯的性質。它用當下的選取預填,而選取離開編輯模式後還留著 —— 所以剛改完第 47 步,數字已經在那裡了

**點標記就開這個面板,而面板是 modal。** 這兩件事是一組的。

在它之前,編輯模式點一個標記只做一件事 —— 設定選取 —— 而面板只從工具列那顆鍵上來。所以**點下去可能完全沒有可見反應**:手勢標記至少會被拖,但等待、暫停、系統按鍵是刻意不可拖的(座標從鄰居推算,拖了不會動,下次重建又跳回原處),那三種的一次點擊回饋是零。於是「等待」的秒數看起來像編輯器改不了的東西 —— 它一直改得動,只是唯一的入口沒有任何地方說。

**modal 的意思是下面不能操作也不能移動:**

- 面板是獨立 window,所以不做 modal 的話,畫布會在**面板沒有實際蓋到**的地方繼續收觸控 —— 一邊打參數一邊把標記拖走,而且「這個標記不能拖」跟「這個標記在面板底下」**分不出來**。這兩件事在改動前就成立,自動彈出只是把它們從偶發變成日常
- 觸控是**吃掉**,不是放行。編輯時畫布蓋滿整個螢幕,放行等於把觸控送給正在被寫腳本的那個 app
- 因此面板**不需要閃避標記**。原本考慮過讓它開在標記的反面,那是在「面板與拖曳同時存在」的前提下才需要的;前提拿掉,置中就夠了
- 換步不用關面板 —— `‹ ›` 本來就在。**要選另一個標記才要關**,出口依舊只有一個
- 只有畫布這條路開面板。`select()` 還有七個呼叫端(刪除落在鄰居上、複製落在複本上、列表、翻頁鍵),沒有一個是「我要看參數」的意思

### 9.6 步驟列表

同樣是置中的大視窗,跟設定頁互斥。**它只做一件事:讓你靠讀找出哪一步不對。**

點一列 = 選取那一步 + 關掉列表 + 開設定頁。列上刻意沒有其他按鍵(沒有複製、沒有刪除):那些作用在選取上,而它們在主選單。

- 做成獨立 window 而不是畫在畫布上:畫上去的版本只能顯示塞得下的尾端、不能捲,而畫布裡的可捲區域會跟拖曳搶垂直手勢 —— 跟工具列把拖曳把手留在 ScrollView 外面是同一個坑
- **不可拖曳,也不需要。** 它曾經是一條小浮動面板,拖曳把手的存在只為了閃避它擋住的東西 —— 而它會擋住東西,是因為它跟設定頁同時在畫面上。現在兩者只會有一個,沒有東西要閃
- 上下步不在這裡也不在主選單:列表可以滑可以點,設定頁有翻頁鍵,再多一組不會更快

### 9.7 實作與原規格的其他差異

- **沒有 120ms 長按門檻。** 改用跟工具列同一套規則:放開時依淨位移判定是點選還是拖曳。M1 踩過的教訓 —— 一旦用「跨過 slop 就鎖定成拖曳」的寫法,手指晃一下再回來就會把 tap 吃掉。同一套規則兩處共用,行為一致。
- **抓取點回到原規格的三個,詳見 §9.10。** 實作一度只有兩個(徽章、箭頭尖端),而徽章是「整段移動」—— 那個組合為什麼不明確,在 §9.10 講。
- **警示區整個取消。** 先做成斜線陰影(而不是原規格的把標記塗黃),後來連斜線也移除 —— 見 §1.3。
- **畫布上沒有雙擊或長按開設定頁。** 討論過:那會讓一個 down 事件同時背著拖曳、單擊、雙擊三種可能的未來,而且為了不讓選取延遲 300ms 還得自己寫仲裁。設定頁從主選單進,那些都不必做。長按目前空著 —— 沒有為了填而填。

### 9.8 系統按鍵是插入的,不是錄下來的

**返回 / 首頁 / 近期 / 通知這四個全域動作只能靠 `⎌+` 手動插入。**

不是為了方便,**這是唯一的入口**:無障礙 overlay 看不到導覽列,實體按鍵也不是觸控事件,所以錄製永遠不可能捕捉到它們。在這顆鍵之前,`GestureDispatcher` 播得出來、`StepText` 有文字、`RepeatableStep` 連重複次數都支援 —— 卻沒有任何地方能建立一個。

- **錄製中也有這顆鍵**,而且按下去會**真的執行那個動作**。理由跟逐手勢補發完全一樣:下層 app 必須跟著你往前走,否則這一步之後錄的每一步都是對著錯的畫面錄的。它一樣尊重「逐手勢補發」那個開關
- **編輯模式不執行** —— 跟 `＋` 和「重錄」同一條規則:編輯時沒有一趟路要同步
- **先問哪一個,而且問在 overlay 上不是 Activity 上。** 跟等待秒數同一個理由:Activity 會把正在錄的 app 推到背景,而那正是下一步要落在的畫面
- **標記跟暫停同一套處理** —— 沒有自己的座標,位置從前後鄰居推導,純粹為了點得到、選得到、刪得到。四種共用一個箭頭圓點,是哪一個由列表文字和設定頁標題說
- **`⎌+` ×3 = 按返回三次**,是重複功能(§9.9)最好的用例之一

### 9.9 單一步驟的重複

**手勢與全域動作可以設定「原地執行 N 次」,以及每次之間的間隔。**

它通過了 §9.11 那個判準,而其他被砍掉的功能沒有:**設定的那一刻你完全知道自己要這個東西按十下**,不需要讀得懂整份腳本。

而且它往正確的方向走:`47 ▸ 輕觸 540,1200 ×10` 是**一行**,不是十行。用複製做出十下是十行還要按九下 —— 這是少數會讓腳本**變短**的編輯功能,而變短是一百步腳本唯一真正有幫助的事。

**`repeat` 與 `delayBefore` 是兩個不同的量,刻意不合併:**

| | 意思 | 來源 |
|---|---|---|
| `delayBefore` | 跟**上一步**之間的間隔 | 錄製時量出來的節奏 |
| `repeatIntervalMs` | **同一步**每次之間的間隔 | 這一步自己的性質 |

一度考慮讓 `delayBefore` 在重複時每次都套用。那會讓同一個欄位在 `repeat = 1` 時是一個意思、大於 1 時是另一個意思 —— 同一個欄位的意義取決於另一個欄位。而且「上一步之後等 2 秒,然後以 200ms 連點十下」會變成表達不出來。

`repeat = 1` 時 `repeatIntervalMs` 根本不會被讀,所以行為跟沒有這個功能時完全一樣。

**幾個決定:**

- **暫停不能重複。** 秒數等待 ×10 就是一個更長的等待;手動暫停 ×10 是停十次。兩個都不是任何人的意思,所以 `PauseStep` 是**不實作 `RepeatableStep`**,而不是實作了再忽略
- **`GlobalStep` 可以重複,而且是最好的用例之一** —— 「按返回三次」退幾層畫面是一步,不是三步
- **調到 2 以上時會自動填入一個可用的間隔**(全域預設 gap)。間隔為 0 的重複會逐次連發,下層 app 會把十下讀成一次多重點擊、或直接丟掉。而且是**寫進步驟**而不是播放時才代入,否則面板會顯示「0 ms」卻不是那樣跑
- **上限 999。** 打錯一個 0 就是一千下
- **每一次之間都過暫停檢查點**,所以暫停和停止在重複中間有效,不是只在步驟之間
- **播放面板顯示 `(3/10)`**,而且只在真的有重複時顯示。重複十次配間隔就是同一個編號停留好幾秒,不顯示會讀成卡住
- **中途某次失敗不改變任何行為** —— 沿用既有規則(回報並繼續)。手勢會失敗通常是整批都失敗,不為這個功能發明新的失敗語意

**這是全 app 第三層重複**,而三層是刻意的:整次執行(`Settings.defaultLoopCount` / `Flow.loopCount`)、片段(`ClipNode.repeat`,M3)、單一步驟(這一節)。範圍不同,而且單步重複沒辦法用另外兩層表達 —— 除非把那一步切成獨立片段丟進流程裡,那在五十步的流程中間是荒謬的。

**每一層的重複都需要自己的間隔,理由同一條。** 整份腳本迴圈之間的間隔是 `Settings.loopIntervalMs`:

- **不能用第 1 步的 `delayBefore` 代替。** 那是「第 1 步之前」的引子,而且它是錄製時填的預設值(第一步沒有前一步可以量),所以拿它當兩圈之間的分隔,結果就是兩圈幾乎貼著跑
- **也不能用 `startDelayMs` 代替。** 那個倒數存在的理由是讓你切到目標 app,一次執行只發生一次;拿它來當每圈之間的間隔,一百圈就是一百次三秒
- **只在圈與圈之間,最後一圈之後沒有。** 實作上就是把 delay 放在迴圈本體最上面、跳過第一圈
- **無限迴圈時最重要** —— 沒有它腳本會不停連續打下去
- **間隔中間也過暫停檢查點**,所以暫停與停止在間隔裡就生效,不用等到下一步
- 播放面板在間隔中只顯示圈數(`↻ 2 / 3`),不顯示步數 —— 那時候沒有任何一步在跑,印 `0 / 100` 會讀成計數器壞了

### 9.10 三個抓取點,每一個都名符其實

**每一個抓取點都長得像它做的事。** 這是這一節唯一的原則,而它是從一個違反它的版本學來的。

```
        ┌─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
        ╷  ◎3 ╲            ╷      ◎ = 觸控圈
        ╷      ╲___        ╷      框內 = 整段移動
        ╷          ╲  ◎    ╷      框 = 路徑的外接矩形
        └─ ─ ─ ─ ─ ─ ─ ─ ─ ┘

        ◎5                        單點:只有觸控圈,沒有框
```

**「框」有兩種,不是同一件事:**

| | 用途 | 誰有 |
|---|---|---|
| **觸控圈** | 圓點標的是一個像素,太小點不到 —— 圈才是你真正按的東西 | 起點、終點、單點,**全部都是同一件事** |
| **線條框** | 框住路徑,是「整段移動」的範圍 | 只有真的有線的步驟 |

| 碰哪裡 | 做什麼 |
|---|---|
| 頭的觸控圈 | 改起點(`withStartAt`) |
| 尾的觸控圈 | 改末端(`withEndAt`) |
| 線條框內其他地方 | 整段移動(`movedTo`)—— 你碰的**就是**整段 |

兩個觸控圈之間**誰近誰贏**,圈贏過框。

**單點只有圈、沒有框。** 沒有線可以框,而跟圈一樣大的框只是在同一個東西外面再畫一圈輪廓,沒有多說任何事。

**觸控圈的意思是「這裡點得到」,不是「這裡拖得動」** —— 所以暫停 / 等待 / 系統按鍵**也有圈**。它們拖不動,但非常需要點得到:選到它是刪除它的唯一途徑。(早期版本不給它們圈,理由是「圈承諾了一個不存在的握把」—— 那是把圈的職責讀錯了。)

### 學到的那件事

實作一度只有兩個抓取點:徽章(= **整段移動**)與箭頭尖端(= 改末端),曲線本體不是目標。原規格砍掉「本體平移」與「起點只改起點」的理由是「起點圓就是序號徽章」加上「本體當目標會有 hit-test 歧義」。

實機測試的回饋是「不好點,而且不明確要點哪」。第一反應是把標記畫大 1.5 倍 —— **沒有用**,因為問題從來不是尺寸:

> 徽章是一個畫在起點上的圓點。它**看起來**是「起點」,**行為**是「整段」。看到的和做到的不一致,放大只會讓它更容易按錯。

而把圓點畫大還有第二個壞處:**它標的是一個像素**,30dp 的圓點在說謊,而且 100 個標記一起放大會讓重疊更嚴重 —— 正好是隔離要解決的問題。

### 兩條原始理由現在的處境

- **「起點圓就是序號徽章」** —— 共用沒問題。數字是標籤不是目標,它跟「改起點」擠在同一個圓點上不會互相搶
- **「本體當目標會有 hit-test 歧義」** —— 這條當初是在**隔離還不存在的時候**寫的。隔離開著時畫面上只有一個標記,跨標記的歧義從架構上就沒有了。而本體改用**外接矩形**而不是「到曲線的距離」,連計算成本和自我交叉的歧義都一起消失,還多一個好處:**矩形畫得出來**,目標不再是隱形的

### 退化情況不需要特例

**沒有可分辨的末端時,只有一個抓取點,而它是「整段移動」。** 單點、長按、多指、以及短到兩端分不開的滑動,全部走這一條。

因為單點沒有「起點 vs 整段」的區別 —— 移動那一個點就是移動整步。這不是特例,是同一條規則在只有一個點時的樣子。

(實作上這也是必要的:單點若走 `withStartAt`,它需要一個末端來當旋轉中心,拿不到就會回傳一個兩點的滑動 —— **步驟型別會因為你推了一下而改變**。)

**衍生標記(暫停 / 等待 / 系統按鍵)只有觸控圈,沒有線條框。** 它們沒有線可以框,而圈是它們被點到、被選到、進而被刪掉的入口。拖曳對它們無效是另一回事 —— 位置是從鄰居推導的,拖了也會彈回去。

### 9.11 編輯能力的天花板是「讀不讀得懂」,不是編輯器有多強

這一節不描述功能,它是**用來砍功能的判準**。

列表上一行長這樣:`47 ▸ 輕觸 540, 1200`。**座標不是意義。** 它告訴你第 47 步在那個位置點了一下,但沒告訴你那一下做了什麼 —— 按到「確認」、展開一個選單、還是關掉一個廣告。

所以任何預設「你知道每一步在做什麼」的功能,實際上做不到:

- **重排腳本** —— 要發現第 5 第 6 反了,得先讀得懂那兩步
- **絕對位置搬移(移到第 N 步)** —— 服務的正是重排
- **步驟型別互轉** —— 你不知道這一步為什麼在這裡,就不會知道它該變成什麼

真正可行的編輯是**小範圍修正**:播放停在第 47 步 → 改它的座標或時間 → 重跑。這是設計要服務好的情境,其他的都是在一份讀不懂的東西上動刀。

**唯一會抬高這個天花板的方向,是讓步驟變得讀得懂**,而不是加編輯功能。具體的路:錄製時順手記下觸點底下那個節點的文字,列表就變成 `47 ▸ 輕觸「確認」`。無障礙服務本來就能讀節點,而讀視窗內容這個能力 M4 為了「等待某段文字出現」已經要做(`NodeFinder.kt`)。

還沒驗證,而且有幾個實際的坑:自繪畫面(Canvas、遊戲)沒有節點可讀、`getRootInActiveWindow` 在錄製熱路徑上有成本、觸點到節點解析之間有時間差。列在 [ROADMAP 待議](ROADMAP.md) 裡,**只記錄不做**。

## 十、錄製流程

`CanvasView` 切到錄製模式,全螢幕攔截,半透明底色提示正在攔截。工具列與播放面板必須疊在畫布之上 —— 同型 overlay 的 z-order 依加入順序,所以進錄製時先確保畫布已加入,再把工具列 remove + add 一次。

一次手勢的生命週期:

```
ACTION_DOWN          記 downTime,開新 stroke
ACTION_POINTER_DOWN  開新 stroke(startOffset = now − downTime)
ACTION_MOVE          各 pointer 取樣,位移 > 4dp 才記(避免點數爆炸)
ACTION_POINTER_UP    該 stroke 收尾
ACTION_UP            全部收尾
  ├─ delayBefore = downTime − 上一手勢結束時間(上限 30s)
  ├─ 產生 GestureStep,【附加】到工作區尾端
  ├─ 加入標記與文字清單一筆
  └─ 若逐手勢補發開啟:
       ├─ 畫布加 FLAG_NOT_TOUCHABLE → updateViewLayout
       ├─ 等一個影格
       ├─ dispatchGesture 並 await callback
       ├─ delay(replayDelayMs) 讓目標 app 完成動畫
       └─ 清除 FLAG_NOT_TOUCHABLE
ACTION_CANCEL        丟棄該手勢
```

錄製開始**不倒數**(你人已經在目標 app);播放才倒數(你人在主 app 或工具列)。

### 10.1 暫停點

**使用者看到的,就只有這一件事:**

> 插一個暫停點。跑到這裡自動停。手動處理完,按繼續。

沒有選項、沒有對話框、沒有設定。按 `⏸+` 就插入,插完錄製自動停下讓你操作,做完按 `⊙` 接續。

**這是 `⏸+` 與 `⏱+` 分成兩顆按鍵的理由。** 資料層是同一個 `PauseStep`(§1.4),但如果共用一顆鍵、按下去先問「幾秒還是等我」,就等於在一個刻意設計成零對話框的流程前面塞一個對話框。手動那顆維持一按就好;要秒數的那顆本來就必須先問,問了才有意義。

`⏱+` **不會停止錄製** —— 停止錄製的用意是讓你動手做事,而等待 N 秒不需要你做任何事。秒數用畫在 overlay 上的數字鍵盤輸入,不走 Activity,所以錄製中插入等待不會把目標 app 推到背景。

**錄製暫停與重播暫停是同一件事的兩面** —— 錄的時候你手動做,播的時候你也手動做。所以「插入暫停點」這一個動作同時定義了這兩個時刻。

```
錄製中,按 ⏸+
  → 插入 PauseStep,錄製停止,觸控放行
  → 你真的輸入驗證碼、真的按下一步,畫面真的前進
  → 按 ⊙ 接續錄後面的步驟

重播中,跑到 PauseStep
  → 停下來,觸控放行
  → 你真的輸入驗證碼
  → 按 ▶ 繼續,接著跑後面的步驟
```

`⏸+` 連帶停止錄製的理由:插它的唯一原因就是接下來要手動做事。純粹想暫停而不插點(滑錯了要滑回來、要看個通知)按 `■` 就好。

**在非錄製狀態按 `⏸+`**:有選取的標記就插在它後面,沒有就插在尾端。

**暫停點不畫準心** —— 它沒有座標。畫成序號連接虛線上的一個小 ⏸ 節點,並出現在步驟文字清單。

那個節點**可以點選,但不能拖曳**。可點選是必要的:編輯模式的 `−` 要有選取才能刪,而在它變成標記之前,`↩ 復原` 是唯一能移除暫停點的手段 —— 偏偏 `⏸+` 一按就停止錄製,把使用者丟進待機。不能拖曳也是必要的:它的位置是從前後鄰居推導出來的,拖了不會改變任何存下來的值,下次重繪就彈回去。

位置的推導見 [ROADMAP §6](ROADMAP.md) —— 夾在兩個手勢之間就落在連線上,連續多個沿線散開,而一個完全沒有手勢的工作區沒有任何東西可以參照,退回畫面中央直排。

`PauseStep.note` 預設空白、**插入時不問**。一個腳本裡有好幾個暫停點時容易忘記各自是幹嘛的,想填再填;空白就顯示「已暫停,請手動處理後按繼續」。

**填的地方在編輯模式的設定頁**:選取暫停點 → `⚏` → 「備註」那一列 → 跳出輸入畫面。走 Activity 而不是 overlay,因為自由文字需要輸入法,而懸浮視窗一律 `FLAG_NOT_FOCUSABLE`(§9.5)。

**插入時不問是刻意的。** 按 `⏸+` 的下一刻,你要的是目標 app 在眼前讓你動手做事 —— 那時候彈一個輸入框只會擋路。而且插入必須維持一按就好(見本節開頭)。在編輯模式插入時會自動選取剛建立的那一步,所以接著按 `⚏` 就是開在它上面。

### 10.2 實作註記:讓暫停點真的能用的三件事

這三件是**實作需求,不是功能** —— 使用者永遠不會看到它們,也不該在 UI 上出現任何對應的開關。但少了任何一件,上面那顆按鍵就是壞的。

**(1) 觸控必須真的放行。** 暫停時 `CanvasWindow` 設 `FLAG_NOT_TOUCHABLE`。這個 flag 的語意是「這個 window 永遠收不到觸控」,所以觸控**穿透下去**給下層 app 與輸入法 —— 名字容易誤讀成「鎖住觸控」,實際是相反的。提示條也畫在這個畫布上,所以它純粹是視覺的,不攔任何東西。

**(2) 工具列必須把鍵盤區讓出來。** 畫布穿透只解決全螢幕那一層,真正會擋住你打字的是工具列:12 顆鍵約佔螢幕 40% 高度、貼著左緣往下延伸,**必然壓在鍵盤的 Q / A / Z 那一整排上面**。而且 `TYPE_ACCESSIBILITY_OVERLAY` 的層級**高於 `TYPE_INPUT_METHOD`**,是工具列蓋住鍵盤,不是反過來。你按 A,按到的是工具列的某顆鍵。

**兩種暫停走不同的路,因為工具列在不在是不一樣的:**

- **錄製中按 `⏸+`** —— 錄製停止、回到待機,工具列還在。所以它**自動**摺疊成一顆 56dp 小球並移到螢幕上半部(y < 40% 高),球面只顯示「繼續錄製」。仍可拖曳,萬一它還是擋到。按下去 `startRecording()` 會把它設回展開,所以不需要另一條復原路徑
- **播放中遇到 `PauseStep`** —— **工具列整個不出現**(§3.4),鍵盤區本來就是空的,不需要摺疊。繼續與停止都在頂部播放面板上,而那條窄面板貼在螢幕頂端,不在鍵盤區

暫停時你只需要「繼續」這一個功能,整排按鍵都沒意義。錄製那條摺疊成球,播放那條連球都不用。

例外:按 `■` 單純停止錄製時**維持展開** —— 你可能是要存檔、進編輯模式、加點,需要整排按鍵。要讓位自己按 `∧`。

**(3) 時間軸不能被汙染。** 你打驗證碼花了 30 秒,恢復錄製後第一個手勢若照實算 `delayBefore = 30000ms`,重播時就會莫名其妙卡 30 秒。所以每次恢復錄製時,把「上一手勢結束時間」重設為恢復的那一刻,恢復後第一個手勢的 `delayBefore` 一律取 `settings.defaultGapMs`。

**恢復錄製立即生效,不倒數。** 靠 `↩ 復原` 救濟誤錄,比讓使用者每次都等 3 秒划算。按 `⊙` 那一下點在工具列上,工具列吃掉了,畫布收不到,不會被錄進去。

**M4 可選優化**:用 `AccessibilityService.getWindows()` 找到 `TYPE_INPUT_METHOD` 的實際 `boundsInScreen`,精準閃避而不是固定移到上半部。要多開 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`,收益不大,先不做。

### 10.3 錄製時的限制(UI 上要提示)

- 工具列、播放面板、步驟清單覆蓋的區域無法錄製 —— 拖走它們
- 錄製中轉螢幕方向 → 中止錄製並提示(座標系會亂掉)
- 快速連續滑動在補發模式下會失準 → 關掉「逐手勢補發」改純盲錄

### 10.4 mode 是狀態,不是推導出來的

**`AppMode.CLIP | FLOW`,持久化,啟動時還原。** 它只有一個定義:**`▶` 會播什麼。** 其他所有差異都是從這句推出來的。

原本它是推導的 —— `currentFlowId != null` —— 而那一行製造了三個問題:

1. **「在 flow mode 但還沒挑流程」無法表示**,所以第一條流程建不出來(新建鍵只在 flow mode 出現)。
2. **每次讀取 / 卸載 / 錄製都在偷偷改模式**,每一個都是別人要記得處理對的隱藏轉換。
3. **「切換模式」根本無法表達**,因為模式不是一個可以設的東西。

現在只有一顆按鍵會改它(§10.5),而所有「什麼被載入了」的規則收在 `engine/Session.kt` 一個物件裡 —— 那個不變式是**兩邊最多只有一邊有東西**,散在呼叫端就是一組要記得的邊,漏一條就是一個 bug(「讀片段忘了卸流程」就是這樣來的)。

**clip mode 操作的對象是 node,flow mode 操作的對象是 clip。** 兩者差一層,所以功能量差很多 —— 這不是「同一種模式裝不同東西」,是兩個模式在處理相隔一層的東西。

**而且兩邊的創作方式天生不對稱,不要硬拉平。** 片段靠**錄製**產生,在別的 app 上面,工具列是它的家;流程靠**排列**產生,需要清單 UI,app 畫面是它的家。所以 flow mode 的按鍵少不是缺東西,是流程的創作不在那裡發生。同理:**空的工作區就是新的片段**,所以「新建片段」只是「清掉現在的」,不是創作入口 —— 首頁不需要那顆鍵。

**沒有「存流程」這個動作。** 編排畫面直接改的就是存起來的那條流程 —— 它是引用清單,裡面沒有會累積的東西 —— 所以流程永遠沒有「未存」狀態,這也是為什麼丟棄的警告只有單邊(§10.6)。

**`⊕` 與 `−` 在兩個模式是不同的名詞**(片段 / 流程)。不另外做圖示,因為名詞跟著模式走。分辨的依據是**按鍵欄最上面那顆模式鍵**。

**`📂` 只列當前模式的那一種。** 原本兩種都列,那是「挑什麼就決定模式」的時代留下的;模式明確之後那是個破口 —— 在 clip mode 挑一條流程等於沒經過模式鍵就清空了工作區,而模式鍵是唯一會先問的地方。

### 10.5 模式鍵是唯一刻意切換的路

位置在**按鍵欄最上面、grip 底下**,而這個位置是規格的一部分:它是唯一會改變其他按鍵*含義*的按鍵,所以周圍的按鍵組換掉時它不能跟著位移。從上往下讀就是「哪個名詞 → 拿它做什麼」。

**圖示顯示你現在在哪個模式,不是按了會去哪。** 顯示目的地的切換圖示,在你不記得方向的那一刻就是歧義的。

**切換會把兩邊都清空**,所以 `clip → flow → clip` 回到一個空的 clip mode。這是目的而不是副作用:讓「按播放會發生什麼」單看模式就能回答,不需要再問兩個載入的東西誰贏。也因此首頁的「已讀取」標記同時最多只有一列會掛著。

**「切過去再切回來會弄丟東西」不是問題,不要為它做跨模式的狀態保留。** 因為**互切沒有使用情境** —— 沒有人為了看一眼流程而切過去再切回來,切模式是「我要改做另一件事」。要的只是有提示(§10.6)。這條是在實作完之後特地確認過的:當時的疑慮是「感受上可能太重」,而那個疑慮把「使用者會不會這樣做」跟「這樣做會怎樣」混成一件事了 —— 後者確實有代價,但前者讓它沒有承受者。

**錄製鍵在 flow mode 不出現。** 它原本在,而且兼任「離開 flow mode 的路」—— 那就是一次隱藏的模式切換。現在出口只有模式鍵一個。

四組按鍵是 **13 / 8 / 13 / 11**(clip idle / 錄製 / 編輯 / flow mode,含 grip)。這個數字用腳本從 `ToolbarView.kt` 的可見性運算式反推,並檢查每個模式都有離開自己的按鍵 —— 不是讀 diff 得來的。讀 diff 漏掉過兩次(`✎` 從編輯模式消失、三顆流程鍵沒進按鍵欄)。

**進入 flow mode 有四條路:**

| 從哪裡 | 怎麼做 |
|---|---|
| 工具列 | 模式鍵(任何時候,不需要先有流程) |
| app 首頁 | 點流程那一列(讀取並進入) |
| app 首頁 | 「新建流程」(建完載入並開編排) |
| 工具列(flow mode) | `📂` 或 `⊕` |

第一條是新的,而它才是根本的那條:其餘三條之前全部依賴「先有一條載入的流程」,結果 flow mode 進不去。

**編排流程有三條路**:首頁流程列的 `⋮ → 編排`(不讀取)、新建流程之後自動進入、工具列 flow mode 的 `✎`(流程已載入)。最後一條原本不存在 —— flow mode 完全沒辦法改排列,得退回 app。

### 10.6 丟棄工作區:一個問句,五個地方

**條件是 `Workspace.dirty`,不是「有沒有步驟」。** 讀進來沒動過的片段已經是存好的片段,丟掉它花的是兩下點擊而不是任何工作 —— 而為那種情況跳警告,會把「按掉警告」訓練成反射,那正是真正該看的那一次被無視的原因。

五個地方共用同一個函式、同一句話、**丟棄並繼續 / 取消**:

| 地方 | 原本 |
|---|---|
| 工具列 `✕` | 不問,而且不清空 |
| 首頁的工具列開關 | 不問 |
| 模式鍵 clip → flow | (新增) |
| `📂` 讀另一個 | 只警告「會取代」,帶步數 |
| `⊕ 開新的` | 只提示「會清空 N 個動作」,帶步數 |

**沒有「存」這個選項。** 存一個新錄製需要名字,名字需要 Activity,於是每一個呼叫端都得把「待辦的動作」帶著出去再帶回來。取消再按 `💾` 是多一下點擊,換掉一個狀態機。

**不帶步數,所以字串反而變少**:原本兩句帶 `%1$d` 的警告合成一句。

**只傳一個標籤給 pad。** `OptionPadView` 底部本來就有自己的取消 —— 每一個 overlay pad 都靠它關掉,它一直都在 —— 所以再傳一個「取消」進去,畫面上就是 `確定 / 取消 / 取消`。**這是 pad 的通用規則,不是這一處的細節**:呼叫端只列出「要做的事」,退出由 pad 提供。同一個檔案裡的流程刪除早就是這個形狀。

而剩下那一顆要**講出結果**而不是同意一個問句。取消消失之後它自己承擔全部語意,而「確定」對著「有修改沒儲存,會丟失」並沒有說它答的是哪一邊。

**答完一律清空,不論答什麼。** 這是下一節的前提。

**`⊕ 開新的` 不再開 Activity。** 它原本只是為了顯示那句「會清空 N 個動作」而開一個畫面,而工作區乾淨時那個畫面問的問題只有一個答案。

### 10.7 復原:離開就清,被殺才問

**明確離開一律清空工作區,所以磁碟上一份 dirty 的草稿只可能是行程死掉留下的。** 檔案本身就是證據,不需要任何旗標 —— `Workspace.clear()` 會把草稿寫回 dirty = false。

> **復原問句出現 ⟺ 上次不是你自己關的,而且當時有未存的改動**

問的時機是**工具列第一次真的出現在螢幕上**,不是服務啟動時:服務可以在任何東西可見之前很久就綁定完成,而一個沒人看得到的問句等於被下一個動作代答了。也不在 app 裡問 —— 工作區只能透過工具列碰到。

**先還原再問,不是先問再還原。** 還原是安全的方向:步驟已經在記憶體裡,所以沒答等於沒損失;反過來「答完才從磁碟載入」會跟第一個寫草稿的動作賽跑。

**清掉復原檔的時機只有明確的使用者動作,不靠 `onDestroy`。** 那個回呼在被硬殺時不會跑,而在低記憶體回收時*可能*會跑 —— 賭它等於讓復原檔在最需要的時候剛好被清掉。代價是:從系統設定關掉無障礙服務、什麼鍵都沒按,下次啟動會多問一句。

**啟動時 mode 還原,內容一律不還原。** 不對稱是刻意的:錄到一半掉了救不回來,流程重挑一下就好。所以 `currentFlowId` **不再持久化**,而工作區草稿只在 dirty 時回來。

### 10.8 首頁不是模式選擇器

**它的工作是把你送進一個有東西的模式,然後讓開** —— 因為對片段做的每件事都發生在別的 app 上面,工具列在那裡。所以**讀取之後就關掉這個畫面**(順手打開工具列;服務沒啟用時不關,那時你要的是那張權限卡)。

**讀取在列上,不在 `⋮` 裡。** 原本是反過來的:點片段列**什麼都不做**,點流程列開編排 —— 主要動作埋在選單裡,而最直覺的手勢一邊是空的、一邊是另一件事。`⋮` 留下的是維護(改名 / 刪除,流程多一個編排)。

**「直接開始(不讀檔)」** 是因為兩個清單都答不了最常見的開場。讓清單當成進入模式的路,破洞剛好開在第一次使用的位置 —— 想錄新的東西時沒有列可以點。

### 10.9 從流程裡編一個片段:深度一層的堆疊

在流程編排裡看到第四個片段的 delay 不對,原本要離開流程、在首頁找到那個片段、修好、再回來找那條流程。現在**點片段名字就打開它,完成就回來**。

**片段開在流程之上,關閉就退回去。** 跟參數卡蓋在畫布上是同一個形狀,也帶來同一個結果:**巢狀時只有一個出口。**

**模式鍵在巢狀時隱藏,而這是重點不是整理。** 留著的話它在那裡有兩個讀法 —— 「兩邊都清空」還是「回到我來的那條流程」—— 而決定是哪一個的是**你怎麼進來的**,那不顯示在任何地方。一顆鍵兩個意思、由看不見的狀態決定,正是當初逼出「mode 要變成明確狀態」的那個 bug。所以巢狀狀態有自己的鍵,而且它說出自己做什麼;圖示刻意不像工具列那顆關閉。

**完成會問要不要存,而它是唯一能提供「存」的丟棄問句。** 一般那句不能(見 10.6):存一個新錄製需要名字,名字需要 Activity,每個呼叫端都得把待辦動作帶出去再帶回來。而走到這裡代表片段是**被載入的** —— 它已經有名字有 id,覆寫不需要打任何字。兩個標籤在 pad 上,沒有狀態機。工作區乾淨時整個問句跳過。

**「另存新檔」在巢狀時隱藏,因為那裡它是個陷阱。** 流程用 id 參照片段,所以另存新的會讓流程繼續指著沒改過的原件,**你的修正看起來完全沒生效**。要變體請從首頁做,那裡沒有流程在等這個答案。

**書籤不是 `currentFlowId`,而且不能是。** 那一個說的是播放鍵跑哪條流程,在 excursion 期間設它就會讓「載入的流程」和「dirty 的工作區」同時存在於兩側 —— 正好是 `Session` 存在的目的要防的事。它是導覽歷史,私有於 `Session`,**每個入口都清掉、只有一個地方設**,而且沒有任何決定 mode 的邏輯讀它。

**進去不問任何事,而那不是漏掉的。** 流程編排每改一下就寫檔,所以流程已經在磁碟上;而 flow mode 下工作區恆為空。兩側都沒有東西會丟。

**重新推導工具列可見集合時抓到一個這次自己造的洞。** 完成鍵在編輯模式下仍然可用(「修好那個 node 再回去」就是整個情境),但模式鍵是**靠在編輯模式隱藏**來避開這件事的 —— 所以回去會在畫布還攔著整個螢幕的情況下改掉 mode。`backToFlow()` 先離開編輯模式。

兩條失敗路徑:**存檔失敗就留在片段上**(而不是走回流程,把那份修改留在一個已經不解釋它的畫面後面 —— 跟存檔對話框失敗時不關閉同一個理由);**流程在片段開著的時候被刪掉**,就落在 flow mode 並說一句,而不是落在沒有地方。

| | 可見鍵數 |
|---|---|
| 待機(clip) | 12 |
| 錄製 | 7 |
| 編輯 | 12 |
| flow mode | 10 |
| **巢狀(在流程裡的片段)** | **12** |
| **巢狀 + 編輯** | **13** |

## 十二之零、存檔放使用者指定的資料夾

**問題**:`filesDir` 會隨卸載一起消失,所以重裝就沒了。而 Android 內建的 `allowBackup` **本來就是開著的**卻救不了 —— 還原只發生在安裝的那一刻(由 Play 或設定精靈觸發,手動裝 APK 那條路不會跑),備份資料綁簽章憑證(debug 與 release 不同),而上傳時機是「充電 + 閒置 + 非計費網路,大約一天一次」。

### 12.0 兩個機制,按版本切,不是「試 SAF 失敗才退回」

**API 29 起 → SAF**(使用者授權的資料夾);**API 28 以下 → `WRITE_EXTERNAL_STORAGE` + 真實路徑。**

不是相容性補丁,是平台真的提供兩種不同的東西:**scoped storage 從 Android 10(API 29)才開始**,在那之前 `WRITE_EXTERNAL_STORAGE` 就是對共用儲存空間的完整讀寫。

分界線放在 28/29 而不是 29/30,因為 Android 10 雖然還能要求 legacy 存取,但那個旗標 Android 11 就不看了 —— 把界線釘在平台真正改變的地方,可以避免一個「行為取決於一個可能被拒絕的請求」的後端。

**舊的那個後端比新的簡單,這跟直覺相反,值得寫下來:**

| SAF 要處理的 | File 後端 |
|---|---|
| id → Uri 對照表 | 不需要,路徑就是位置 |
| `"wt"` 截斷坑 | `writeText` 本來就截斷 |
| `createDirectory` 生出 `clips (1)` | `mkdirs()` 對已存在目錄是 no-op |
| 卸載收回授權 | 沒有授權可收 |
| **外層要使用者自己建** | **我們可以建** |

最後一列是重點:那個限制**只是 SAF 的限制**。

**而這是被實機逼出來的,不是預先設計的。** 一台 Android 7 上 `ACTION_OPEN_DOCUMENT_TREE` 只列得出「最近」—— 而「最近」列的是檔案,對挑資料夾的選擇器來說永遠是空的 —— 於是整個功能在那台**無法設定**。試過 `SHOW_ADVANCED`(那是選擇器 ⋮ 選單「顯示內部儲存空間」對應的 extra)沒有用,那台的 DocumentsUI 沒有把 `ExternalStorageProvider` 的根目錄露出來。而**沒有別的槓桿**:可持久化的授權只能由選擇器的回傳結果產生,不能自己組一個 tree Uri;`EXTRA_INITIAL_URI` 是 API 26 才有的。

**API 28 以下的路徑是固定的 `/sdcard/TapFlow`,由我們建立。** 「可以自己挑資料夾」從來不是目標 —— 目標是重裝不消失、而且放在使用者能自己備份的地方,一個已知路徑兩件都滿足。可以挑是 SAF 的授權模型逼出來的,而這個後端沒有那個模型。

**不放在 `Android/data/<package>` 底下。** 那裡不需要權限,但會隨 app 一起刪掉,正好抵銷掉整件事的目的。

兩邊的磁碟配置**完全相同**(`clips/<名稱>.json`),所以資料夾在兩台裝置之間可以直接複製。

### 12.1 一份,不是兩份

**使用者指定的資料夾裡的那一份就是唯一一份。** 不做內部鏡像 —— 鏡像會製造一個兩份不一致而且沒有人能裁決的狀態:資料夾看起來權威,卻可能比 app 顯示的舊,而重裝後從它還原就靜默拿到舊資料。一份就沒有這個狀態。

```
資料夾/                     ← API 29+ 是他自己建、自己選;API 28- 是 /sdcard/TapFlow,我們建
├─ clips/簽到腳本.json       ← clips/ 與 flows/ 兩層都由我們建
└─ flows/早晨三連.json
```

| | 放哪 | 什麼時候碰 |
|---|---|---|
| 工作區草稿、設定、prefs | `filesDir` | 照舊,錄製的每一步 |
| 存好的片段與流程 | 指定的資料夾 | **只有存檔、讀檔、顯示清單** |

錄製、編輯、播放工作區**完全不碰外部**。所以「外部比本機檔案慢」的代價只在使用者主動要求的地方付。

`settings.json` 留在內部,因為抓取外圈大小與工具列大小是**這台裝置的物理屬性** —— 跟著同步到平板上會是錯的。代價是設定不隨重裝回來。

### 12.2 檔名是裝飾性的

片段的身分是 `id`,它在 JSON **裡面**。檔名用片段名稱,純粹是為了讓打開那個資料夾的人看得懂 —— 那正是讓他自己選資料夾的意義。**讀取時完全不看檔名**,名字和 id 都從內容拿。

這一個決定不是解決三個問題,是讓它們不存在:

| 顧慮 | 檔名裝飾化之後 |
|---|---|
| 兩個片段同名 | provider 自己加後綴,我們收下它給的名字 |
| 名稱有 `/` `:` `*` | 清掉、去空白、截到 60 字、空的話有 fallback |
| 改名時檔案改名失敗 | 檔名過期而已,**不是錯誤**。記 log,不當成存檔失敗 |

另外記一份 id → 文件 Uri 的對照表。刪除和覆寫都要找到那個檔,而 `findFile()` 每次呼叫都會列舉整個目錄。

**這條規則原本有一個例外,而那個例外是型別。** `Kind(val folder: String)` 把「這是 clip 還是 flow」編碼在目錄名裡,所以位置對某一件事是承重的 —— 跟這一節說的相反。移到副檔名之後(見 12.10)例外沒了:**檔案自我描述,位置對 app 完全沒有意義。**

### 12.3 三個 SAF 的坑

**① `"wt"` 而不是 `"w"`。** 這是 SAF 最常見的資料損壞來源:`"w"` 不保證截斷,把較短的 JSON 寫在較長的上面會留下前一份的尾巴,整個檔 parse 不起來。而且**不是機率問題** —— 刪掉一個步驟就會讓檔案變短。

**② 先 `findFile` 再 `createDirectory`。** 對已存在的名稱呼叫 `createDirectory`,`ExternalStorageProvider` 會給你 `clips (1)`。一旦分岔成兩個目錄,一半的片段就從清單上消失了。

**③ Android 11+ 不讓你選 `Download`,也不讓你選內部儲存的根目錄。** 所以引導文案必須說「請選一個子資料夾,例如 `Documents/TapFlow`」—— 選了被拒絕的位置,使用者會讀成這個 app 壞了。

這三個坑**都只存在於 SAF 那一邊**(§12.0)。

### 12.4 為什麼不在首次啟動就強制指定

一度打算這樣做(而且那樣 `InternalStore` 就完全不必存在,只有一個後端)。放棄的理由是**一個還沒被試過的 app 前面擺一個檔案選擇器,那是收費站**,而按取消時只能再問一次。

改成**按 `💾` 或 `📂` 時沒有資料夾才問** —— 需要它的那一刻才要。而這順帶關掉一個漏洞:強制引導只擋得住 app,擋不住服務(開機後無障礙服務會自己重新綁定,`overlayEnabled` 存在內部 prefs 所以工具列照樣出現),於是會有一個背後沒有儲存空間的工具列。錄製不需要資料夾,只有存檔需要,所以那個狀態現在是合法的。

**沒有搬移機制。** 選一個已經有東西的資料夾,那些就是你的片段與流程;選一個空的,就從空的開始。換資料夾等於舊的抓不到 —— 這是刻意的,不是漏洞。

### 12.5 存檔失敗的安全網已經存在

`commit()` 有三種結果而不是兩種,而**把「失敗」跟「沒有東西可以存」分開是重點**:它們原本共用一個 `null` 回傳,所以資料夾讀不到的那天,訊息會說「沒有東西可以存」—— 那不只是沒幫助,是事實的反面。

**`dirty` 只有在寫入落地之後才會清掉。** 於是外部寫入失敗時工作區仍然是未儲存的,§10.7 的復原草稿自動接手,而使用者被要求重選資料夾。不需要新機制。

寫入失敗也會把「資料夾可用」這個旗標翻掉,而那個旗標是 flow(不是布林欄位),所以正在存檔的畫面會**自己變成「重選資料夾」** —— 沒有人需要在每個呼叫端記得接這條線。

### 12.6 大小:量過的,不是猜的

`prettyPrint` 關掉,因為量出來差 5.3 倍:

| | 大小 |
|---|---|
| 一個點擊 | 383 B |
| 一個滑動(60 取樣點) | 8 KB |
| 一個 100 步片段(80 點 + 20 滑) | **250 KB** |
| 20 個這種片段,pretty | 5.5 MB |
| 同上,compact | **1.0 MB** |

滑動貴是因為每個取樣點 pretty-print 之後大約 200 B。而**一個片段一個檔**也是這個數字決定的:存一個片段寫 250 KB 而不是整個 5.5 MB,少 20 倍;寫壞了只損失一個片段。`flows/` 也一個檔一條,理由不是大小(流程只有引用,幾 KB)而是一致性 —— 既然「打開資料夾看得懂」是前提,流程擠在一個檔裡就自我矛盾。

**沒有做 temp + rename 的原子寫。** 有了一個片段一個檔之後,最壞情況從「所有片段一起沒」變成「一個片段壞掉」,而 `renameDocument` 在各家 provider 上行為不一致,自己也有失敗模式。真正會發生的不是行程被殺,是 provider 中途失敗 —— 那需要的是講話,不是原子性。

### 12.7 服務永遠不需要叫出資料夾選擇器

服務唯一會寫外部的時機是「某個東西已經被載入」(例如 flow mode 刪流程),而東西能被載入就代表資料夾選過了。`💾` 和 `📂` 都走 `WorkspaceDialogActivity`,選擇器在那裡有宿主。

這條要守住:從無障礙服務叫 `ACTION_OPEN_DOCUMENT_TREE` 需要 `FLAG_ACTIVITY_NEW_TASK`,而且會把正在錄的 app 推到背景。

### 12.8 順帶:匯出匯入大部分做完了

那個資料夾裡的 `<名稱>.json` **本身就是匯出格式**,所以 M4 的「匯出匯入 JSON」縮到只剩驗證與 remap。ROADMAP 記著的三件事(JSON 變成外部契約、沒有 `schemaVersion`、重複 id 是最尖的邊)**現在就生效了**,因為檔案從一開始就在使用者摸得到的地方 —— 所以讀取必須容忍壞檔:跳過、記 log、不要讓一個壞檔擋掉整個清單。

### 12.9 跳過壞檔沒問題,靜默跳過才是問題

容忍是對的,**靜默**不是。而那個靜默正是實機上遇到的那次遺失的形狀:非正常關機,下次啟動片段庫是空的,什麼都沒說。

從首頁看,**「檔案壞了」跟「這個片段從來沒存過」完全一樣**,而兩者要做的事相反 —— 壞掉的那個**檔案還躺在資料夾裡**,而且檔名是你自己取的。

所以 `loadLibrary` 回報數量,而數量是**減出來的**:列到的檔案數,減掉解析成功的物件數。不放一個計數器進 `decode()` —— 它沒有理由知道自己正在被統計,而一個獨立的計數器會跟它描述的那份清單走散。

顯示在兩個會「少東西」的地方:首頁的清單上方,以及 `📂` 的讀取清單上方,錯誤色。

**那個更窄的靜默已經補掉了**(見 12.10):`list()` 現在回報自己讀不出來或進不去的數量,跟解析失敗的減法加成一個數字。從使用者那一側它們是同一件事 —— 資料夾裡有東西,清單裡沒有。

### 12.10 資料夾是一棵樹,型別在副檔名上

那個資料夾是使用者的,所以裡面怎麼排是他的事。片段可以在根層,也可以在他自己開的任何子資料夾裡,`list()` 走整棵樹。

**型別因此必須離開路徑。** 原本是目錄(`clips/` / `flows/`);檔案能放在任何地方之後,父目錄就不再說明檔案是什麼。改成副檔名 `.clip` / `.flow` —— 而那也順便消掉 12.2 的那個例外。

**一次走完,兩種一起出來。** 走樹是昂貴的部分,而每一個要 flow 的畫面都要 clip(流程列要寫「3 個片段 · 47 個動作」),所以分兩次呼叫就是同一批目錄走兩遍 —— 在 SAF 上每個目錄是一次 IPC 往返。`Entry` 帶著自己的 kind,`Repo` 再分。

**上限 200 個目錄,而且超出的數量會被回報。** 資料夾是使用者的,可能很大。有上限但不靜默 —— 靜默的上限會被讀成「你的片段庫就這些」。同一個計數器順便擋掉 symlink 迴圈(`File.listFiles()` 會跟著走)。

**遞迴讓「掃得完整」變成播放的正確性要求,而這不是潔癖。** 流程用 id 對著記憶體裡那份庫解析,所以**一個進不去的目錄不會表現成「資料夾讀不到」,而是表現成某條流程說它的片段不見了**。所以那個缺口必須看得見 —— 這就是上面那個數字為什麼要把「進不去的目錄」也算進去。

**位置對 app 依然沒有意義。** `folderOf()` 只有兩個列清單的畫面在讀,`FlowPlan` 從來不問片段住在哪。這是資料夾維持「一種看法」而不是結構的一部分的原因,也是**改名與「刪除會從每條流程剪掉」完全不用改**的原因。

**`createFile` 用一個 `MimeTypeMap` 不認識的 MIME type。** `ExternalStorageProvider.createDocument` 會從 MIME type 推出副檔名然後接上去,所以 `application/json` 會把 `登入.clip` 變成 `登入.clip.json` —— **寫進去了但認不出來**,可用的結果裡最糟的一個。不認識的 type 會讓名字原封不動。`Kind.matches()` 兩種都收,以防別的 provider 照樣加。

**寫入的資料夾只決定新檔案去哪。** 已經認得的東西**在它原本的位置**被覆寫,所以在檔案管理員裡搬動檔案照樣能用,存檔也不會把你正在編的東西搬走。

一個例外,只在 SAF:認得的那份文件不見了的時候,覆寫會失敗然後**重建**檔案 —— 重建在當前工作資料夾,因為 document Uri 不會把自己的父層交出來,沒有東西可以「重建在它旁邊」。所以一次需要重建的存檔**可以**把片段搬到工作資料夾。文件化而不是修掉:替代方案是為了一條只有「存檔時檔案剛好被刪掉」才走到的路,把資料夾一路穿過 `remember()`,而把片段救回來值得那個代價。`FileLibrary` 沒有這條路 —— 那邊寫失敗就是失敗,因為目標是一個仍然有效的路徑。

## 十三、實作分期

### M1 — 能錄能播(最大風險期)

服務 + 三個 window(含 overlay fallback、吸邊、摺疊、邊緣把手)+ 工具列 + 播放面板 + 計時器 + 錄製與逐手勢補發(單指)+ **`⊙` 接續錄製** + **`⏸+` 插入暫停點** + **`↩` 復原** + 標記顯示(唯讀)+ 步驟文字清單 + `👁` 三段密度 + 工作區與自動草稿 + `💾` 存成片段 + 播放工作區 / 片段 + 迴圈次數 + 暫停 / 停止 + 音量鍵備援 + 螢幕常亮 + GitHub Actions。

**暫停點提前到 M1**(原本排 M3)—— 沒有它就錄不了任何「中間需要人工」的多層流程,而那正是這個 app 跟市面上同類產品的差異點。它也是全 app 唯一的暫停機制,所以後面各期都不用再蓋暫停相關的東西。

**驗收重點,這三點決定後面設計是否要調整:**

1. 逐手勢補發在實機上的手感 —— 頓挫是否可接受、畫面是否確實前進
2. `FLAG_NOT_TOUCHABLE` 切換是否可靠地讓畫布放行觸控
3. 錄 50+ 步時標記是否還看得清楚、觸控是否還流暢

### M2 — 螢幕上直接編輯

`✎` 編輯模式 + 標記 hit-test 與拖曳 + `＋` 擷取手勢新增一步 + `⧉` 複製 + `⎌+` 插入系統按鍵 + `−` 刪除 + 步驟設定頁(類型 / 座標 / 等待秒數 / 備註 / 時長 / 延遲 / 重複次數與間隔 / 前後移一格 / 複製 / 刪除 / 翻頁 / 跳到第 N 步)+ 步驟列表 + 隔離 + 全域設定畫面(預設值、隨機抖動、大小 / 不透明度、亞光)。

### M3 — 流程

Flow 資料層 + 流程編排畫面 + 流程展開與執行 + 兩層迴圈 + flow mode 的按鍵組。

**流程層不新增任何執行器。** 流程展開成一條步驟清單交給既有的 `Player`(`FlowPlan`),所以它直接繼承每圈間隔、碰到暫停、單步重複、從第 N 步開始 —— 寫第二個執行器等於把那四件事再實作一次,然後兩邊開始漂。

**流程層也不新增暫停機制** —— `PauseStep` 已經涵蓋。而預留的 `pauseAfter` 旗標**不用做了**:`ClipNode.delayBefore` 更一般化地解掉同一個問題(它是長度而不是布林)。

**展開時逐 clip 各自做座標縮放。** 每個 `Clip` 有自己的 `screen`,而 `Player` 只吃一個 —— 不這樣做,混了兩個錄製來源的流程會整條用其中一個的比例播出去。這是既有的線性縮放套用在每個 clip 上,不是換機重算(那屬於匯出時的工作)。

### M4 — 條件等待與多指

開 `canRetrieveWindowContent` + `AwaitTextNode` + 畫面文字掃描輔助 + 多指錄製與重播 + 片段 / 流程匯出匯入 JSON。

可選(視實測需要再決定):播放中面板自動避讓、`willContinue` 分段 stroke 提升滑動擬真度。

## 十四、已知限制

1. **部分遊戲 / 金融 app 會擋注入手勢**(檢查 `FLAG_WINDOW_IS_OBSCURED`、`getToolType`,或直接偵測無障礙服務啟用),重播會無效。無 root 無解。
2. `dispatchGesture` 時序精度受系統排程影響,抖動約 ±10~30ms。要求毫秒級精準的場景不適用。
3. 單一 stroke 內的速度變化不會完整保留(`GestureDescription` 沿路徑均速插值)。若實測滑動手感差,M4 可改用 `willContinue` 分段 stroke。
4. 純座標重播,不做圖像識別,換機型只能線性縮放。
5. 條件等待只讀得到 app 願意暴露給無障礙的節點;Canvas / 遊戲引擎自繪 UI 讀不到。
6. **工具列與播放面板覆蓋的區域,錄製時錄不到、播放時該步驟會被吃掉。** 請拖到空白處(§1.3)。
7. 銀行、密碼輸入等帶 `FLAG_SECURE` 的畫面會隱藏所有 overlay,注入手勢通常也會被擋。
8. **注入的手勢不會跟真實觸控疊加,真實輸入會取消它。** 框架的 `MotionEventInjector` 一收到真實輸入就取消所有在飛的注入手勢 —— 這是平台行為,app 改不了。所以播放中碰螢幕會讓那一步失效。
   - 無障礙服務仍然**拿不到其他 app 的觸控事件**,所以偵測不是直接的;但「手勢被取消」本身就是一個訊號,而且在正常裝置上幾乎只有這一個成因(其他成因都是本 app 控制得住的:不會同時派送兩個手勢、重播期間刻意不動畫布;而缺少注入器那一種在時序上先被分出去了)。
   - 因此播放中一旦有手勢被中途取消,**播放會暫停並說明原因**,而不是報告失敗然後繼續。那一步沒有落下,繼續跑等於後面每一步都對著錯的畫面執行。**被中斷的那一步不會自動重做** —— 中途取消的滑動可能已經送出一半,重送不安全。
   - 這一條原本寫的是「偵測不到,所以沒有碰到就暫停的保護」,那是錯的。
9. 不支援文字輸入自動化(§11)。

## 十四之二、系統層故障:手勢注入器卡住

**不是這個 app 能修的問題,但必須認得出來,否則會浪費大量除錯時間。**

`dispatchGesture` 依賴 `MotionEventInjector`,而它隨無障礙輸入過濾鏈一起安裝。`AccessibilityManagerService` 取用它時會等最多 `WAIT_MOTION_INJECTOR_TIMEOUT_MILLIS`(**1 秒**),等不到就直接回報手勢失敗。

**判準:失敗時間固定在 ~1010ms,與手勢長度無關。**

```
dispatch strokes=1 [938,1170..938,1170 106ms]
  -> CANCELLED after 1010ms of  106ms      ← 點擊
  -> CANCELLED after 1009ms of 1147ms      ← 長滑動,同一個時間點
```

一個 106ms 的點擊不可能「執行到一半被打斷」1010ms。看到這個就不要往程式碼裡找。

**處理順序**:toggle 無障礙服務 → **重開機(實測有效)** → 重新安裝。

> 這個狀況實際上耗掉了四輪除錯。誤導的關鍵有兩點:一是原本的錯誤訊息把「該 app 拒收注入手勢、需要 root」當成結論寫死,而那只是眾多可能之一;二是「上一個好的 commit」與「第一個壞的 commit」之間看似有因果,實際上那個 diff 完全沒有碰到手勢派送路徑,真正的變數是重新安裝 APK 導致服務重新綁定。
>
> 教訓:**當 diff 裡找不到任何相關的東西時,先懷疑環境而不是繼續猜程式碼。** 而讓環境自己說話的工具就是 §14.3 的診斷紀錄。

## 十四之三、診斷紀錄

主畫面最下方的「診斷紀錄」記下引擎的近期時間軸:擷取了幾個 stroke、畫布何時釋放、派送的座標範圍與時長、結果與耗時。按錄製或播放會清空重新計時,可一鍵複製(含版本號)。

存在理由:**手機上拿不到 logcat,而 toast 只能講一句話。** 沒有它的時候,每個假設都要出一個 build 才能驗證;有了它,一次就定案。

刻意做成純文字、有上限、沒有任何功能依賴它 —— 它是除錯工具,不是產品功能。

## 十五、驗證方式

**編譯**:推上 GitHub → Actions 跑 `gradle assembleDebug` → 下載 `app-debug.apk` artifact。

**實機驗收(每期)**

- **M1** — 開無障礙 → 工具列出現 → 按 `⊙` 錄「設定 → Wi-Fi → 返回」→ **確認錄製時畫面確實前進** → 螢幕上出現 1/2/3 準心且文字清單同步 → `👁` 三段切換正常 → `↩` 復原 → 按 `■` 停止,做點別的事,再按 `⊙` 確認**接續**而非重來 → 按 `💾` 存成片段 → 按 `▶` 確認動作重現 → 頂部面板計時器與進度正確 → 音量鍵暫停 / 停止 → 收起成邊緣把手再點回來 → 殺掉服務再開,確認工作區草稿還在 → 連錄 50+ 步確認不卡
- **M1(人工介入專項,最關鍵的一項)** — 找一個需要輸入文字的畫面,錄到該步按 `⏸+` → 確認錄製自動停止、工具列自動摺疊成球並移到上半部 → **叫出鍵盤,把 Q / A / Z 那一整排每個鍵都按一次,確認沒有任何一鍵被工具列吃掉** → 真的輸入完 → 按球上的 `⊙` 接續錄後面幾步,確認工具列展開回原位 → 確認接續後第一步的前置延遲**不是**你打字花掉的那幾十秒 → 存檔重播 → 確認跑到該步會停下、提示條出現在頂部且不擋觸控 → 按繼續確認接續執行 → 換成「不顯示提示」再測一次
- **M2** — 按 `✎` 進編輯模式 → 拖動某個準心 → 播放確認新座標生效 → `＋` 擷取手勢加一步 → `⚏` 設定頁改時長與延遲 → `☰` 列表選第 47 步 → 開隨機抖動 150px,播放時觀察落點確實散開 → 開亞光,確認注入手勢仍然有效(亞光層不吃觸控)
- **M3** — 分三次錄三個片段,其中一段尾端放暫停點 → 首頁建流程 → 加入三個片段、排順序 → 某一列設 ×3 每 5 秒 → 按模式鍵切到 flow mode(確認會警告工作區未存)→ `📂` 讀取流程 → 確認 `▶` 變成流程圖示、按鍵剩 11 顆、`⊙` 不見了 → 播放,面板顯示 `片段 2/3 步驟 10/30` → 跑到暫停點會停、按繼續接續 → 按模式鍵確認切回 clip mode 且兩邊都空 → 刪掉其中一個片段,確認流程那一列跟著消失且刪除確認框說了有幾條流程在用
- **M4** — 插入「等待出現『登入成功』」節點,測命中與超時轉暫停兩條路徑 → 錄雙指縮放並重播 → 匯出 JSON 再匯入,確認一致
